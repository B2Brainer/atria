# Increment 7 — Prototype Validation

Status: Approved

Agentic workflow for this increment follows the established process, adapted to its validation nature: spec-creator (this document) → human approval → Claude Code validation execution (no new production functionality) → test-engineer independent verification → code-reviewer independent review → human final approval → `commit` skill → Marshal PR gate (`marshal pr`, the sole Marshal touchpoint in this regular increment cycle per the operator-authorized exemption recorded in `CLAUDE.md` §0 and `.marshal/context/brief.md` — standalone `marshal plan`/`marshal-cpd` are not required).

## Objective

Verify the complete Atria prototype — as implemented across Increments 1–6 — against the established prototype requirements (`atria-t0.md`: AI usage system, Software design, Architecture, Infrastructure, Technologies, Design) and against each increment's own approved acceptance criteria, producing a consolidated, traceable prototype validation report that states, for every validated item, whether it is verified, partially verified, failed, or unverified/PENDING.

This is the final increment of the Implementation Plan and corresponds to the point in the Systematize → Automate → Optimize construction method (`atria-t0.md` §8) where the already-systematized and automated prototype is checked for sufficiency of evidence before any future Optimize-phase work is considered. Increment 7 produces that evidence; it does not perform optimization itself.

## Scope

**Included:**

- **Re-execution of established automated verification** across the whole repository in its current integrated state: the full `pytest` suite (`tests/`), `ruff check`, the full `vitest` suite (`desktop/`), and `eslint` (`desktop/`), run once against the merged `main` state to confirm the increments integrate correctly together (not only individually, as already gated increment-by-increment).
- **Cross-increment integration and system-level validation** that increments 1–6's own acceptance criteria did not — and structurally could not — each individually exercise end-to-end:
  - The complete Clean Interaction → AIUsageCycle/InteractionRecord persistence workflow exercised through the real, packaged desktop application (not only through `tests/integration/test_end_to_end_clean_interaction.py`'s backend-only path), confirming the data flow described in `AI usage system.md` and the `data/code.md` class diagram holds end-to-end: UI → `InteractionManagement` → `AIProviderAdapter`/`CredentialAdapter` → `InteractionRecordManagement` → `PersistenceAdapter` → SQLite, and back.
  - Interaction independence (statelessness of a Clean Interaction): confirming a second Clean Interaction is not influenced by state from a prior interaction (no provider-side conversation carry-over, no cross-interaction core-side mutable state), consistent with the `AI usage system.md` definitions of "Clean AI Model" and "Clean Interaction".
  - Execution metrics (`ExecutionMetrics`: `input_tokens`, `output_tokens`, `duration`, `cost`) are populated and persisted on a real provider round-trip, not only on mocked/unit-level paths.
  - Credential management exercised against the real macOS Keychain adapter (not only the port's test double) for store/retrieve/delete, from both the development run and the packaged application.
  - The packaged, distributed application (Increment 5/6 deliverable) launched from an installed artifact and operated through a representative Clean Interaction and record-retrieval session.
- **Architectural and engineering-integrity audit**: confirming the implemented `core/`, `adapters/`, `api/` boundaries still match the established Hexagonal Architecture / Adapter pattern (`structure/code.md`, `interfaces/code.md`) — no adapter-layer concern (SQL, HTTP, Keychain, Electron/IPC) leaking into `core/`; `core/ports/` contracts (`AIProviderPort`, `PersistencePort`, `CredentialPort`) unchanged in shape from `interfaces/code.md` and from Increment 2's approved specification; dependency direction intact (`tests/test_import_boundaries.py` re-affirmed, not re-authored).
- **Consolidated gap analysis**: identifying, for every established prototype requirement and every Increment 1–6 acceptance criterion, whether it is (a) verified by existing, reusable evidence from increments 1–6 (test suite + CI + review-gate record), (b) newly verified by this increment's system-level/acceptance validation, (c) partially verified (evidence exists but is narrower than the requirement), (d) failed (a defect found), or (e) unverified/PENDING (cannot be exercised in this environment — e.g., Increment 6's real Apple Developer signing/notarization credentials remain absent).
- **Defect classification and disposition**: any defect found during this increment's validation is triaged as either (i) **prototype-compliance-blocking** — a deviation from an established requirement or an approved Increment 1–6 acceptance criterion, which must be corrected (via the standard specification → implementation → verification → review cycle, scoped as a corrective-maintenance change to the affected increment's area, not as new Increment 7 functionality) before this increment can close — or (ii) **future/post-prototype improvement** — a non-blocking observation (e.g., a usability refinement, a performance optimization opportunity, additional test coverage beyond what was specified) that is recorded in the validation report as out of scope for this increment and deferred to future development.
- **Final Prototype Validation Report**: a single deliverable artifact (`specs/increment-07-validation-report.md` or equivalent, produced during implementation of this increment, not authored in advance by this specification) consolidating: the traceability matrix (requirement/AC → verification method → result), the list of blocking defects and their resolution status, the list of deferred observations, and the explicit PENDING register (items that remain unverifiable in this environment, carried forward from Increment 6 and any newly identified during this increment).

**Excluded:**

- Any new `core/`, `adapters/`, or `api/` business functionality, new port, new data-model field, or architectural change. This increment validates; it does not extend.
- Refactoring undertaken for its own sake. A refactor is only in scope as the correction for a blocking defect this increment's validation identifies, under the standard workflow.
- Optimization-phase work (`atria-t0.md` §8 "Optimize"): performance tuning, UX polish, or architectural evolution beyond what is needed to close a blocking defect. Optimize is explicitly gated on this increment's evidence and begins only after this increment closes and is reviewed by the operator.
- Resolving Increment 6's PENDING real Apple Developer Program signing/notarization verification: this increment cannot manufacture Apple Developer credentials. It must re-confirm the PENDING status is still accurate (the gap has not silently changed) and carry it forward in the Final Prototype Validation Report as still unverified — it must not be marked passed by default or by the passage of time.
- Any change to `Brainer/teoria/` (authoritative documentation, read-only) or to any already-approved `specs/increment-0[1-6]-*.md` acceptance criteria. A defect this increment finds against an approved acceptance criterion is reported as a defect against the implementation, not resolved by editing the criterion.
- Windows/Linux validation: out of scope, consistent with the established macOS-only Infrastructure.
- Any standalone `marshal plan` or `marshal-cpd` invocation for this regular increment, per the operator-authorized exemption already recorded in `CLAUDE.md` §0; `marshal pr` remains the PR gate for this increment's integration like every other.

## Expected Behavior

1. **Full-suite re-execution confirms integrated correctness.** Running the complete `pytest`, `ruff check`, `vitest`, and `eslint` suites against the current `main` state succeeds with no failures attributable to cross-increment integration (a regression between increments, not previously caught because each increment's own gate only saw its own diff).
2. **End-to-end Clean Interaction workflow confirmed through the packaged application.** A user-equivalent session — launching the installed desktop artifact, configuring a provider credential, initiating a Clean Interaction, observing its result and `ExecutionMetrics` in the interface, and retrieving the persisted `InteractionRecord` after an application restart — completes successfully and matches the `AI usage system.md`/`data/code.md` data flow.
3. **Interaction independence confirmed.** Two sequential Clean Interactions, the second following the first within the same `AIUsageCycle` or across cycles, show no observable state leakage from the first into the second (no carried-over provider conversation context, no core-side mutable state affecting the second interaction's input/output).
4. **Architectural boundaries confirmed intact.** `core/` contains no adapter-specific (SQL, HTTP, Keychain, Electron/IPC) code; `core/ports/` signatures match `interfaces/code.md`; dependency-direction checks (`tests/test_import_boundaries.py`) still pass against the current `main` tree.
5. **Gap analysis is exhaustive and status-explicit.** Every established requirement (`atria-t0.md` top-level bullets) and every Increment 1–6 acceptance criterion appears exactly once in the traceability matrix with one of: Verified / Partially Verified / Failed / Unverified-PENDING — no requirement or acceptance criterion is silently omitted, and no previously-PENDING item (Increment 6's real signing/notarization verification) is marked Verified absent the real credentials actually being exercised.
6. **Defects are disposed correctly.** A defect found during validation is recorded with its classification (compliance-blocking vs. deferred improvement); a compliance-blocking defect is corrected through the standard specification → implementation → verification → review cycle before this increment closes, and the correction is re-validated; a deferred improvement is recorded in the Final Prototype Validation Report without blocking closure.
7. **Final Prototype Validation Report produced.** The report exists, is internally consistent with the evidence gathered (every claim in it traces to a specific test, CI run, or manual verification step reproducible from this specification), and explicitly lists any item still PENDING at the time this increment closes.

## Acceptance Criteria

1. The full `pytest` suite, `ruff check .`, the full `desktop` `vitest` suite, and `desktop` `eslint` all pass when run against the current `main` state in one combined session (not relying solely on each increment's own historical, individually-scoped CI run).
2. A traceability matrix exists, in the Final Prototype Validation Report, mapping each `atria-t0.md` top-level requirement bullet (AI usage system: 2 items; Software design: 6 items) to the verification evidence confirming or disconfirming it, with an explicit status per item.
3. A traceability matrix exists, in the Final Prototype Validation Report, mapping each Increment 1–6 acceptance criterion (by increment and item number) to its verification status, reusing increments 1–6's own recorded verification evidence (test files, CI run, `.marshal/reviews` and `.marshal/pr-gate` records) where that evidence already covers the criterion, rather than re-deriving unit-level coverage from scratch.
4. A documented, reproducible end-to-end session demonstrates: launching the packaged desktop application, storing a real or test-double provider credential via the Keychain-backed adapter, initiating a Clean Interaction, observing a persisted `InteractionRecord` with populated `ExecutionMetrics`, restarting the application, and retrieving that same record — with each step's observed outcome recorded as evidence (screenshot, log excerpt, or test transcript) in the report.
5. A test or documented manual procedure demonstrates two sequential Clean Interactions do not share provider-side or core-side state: the second interaction's request/result pair shows no residue (e.g., no reference to the first interaction's input appearing in the second's output when none was supplied) from the first.
6. A static/code-level check confirms no `adapters/`-specific import or concern (SQLAlchemy, HTTPX, Keychain-binding, Electron/IPC) appears inside `core/`, and that `core/ports/` method signatures (`AIProviderPort.execute`, `PersistencePort.save`/`get`/`list_by_cycle`, `CredentialPort.get`/`store`/`delete`) are unchanged from `interfaces/code.md` and Increment 2's approved specification.
7. The Final Prototype Validation Report explicitly carries forward Increment 6's PENDING real Apple Developer Program signing/notarization verification as still Unverified/PENDING (confirmed not silently resolved since Increment 6 closed), together with any other item this increment newly finds unverifiable in this environment — none reported as Verified without the underlying real-environment check having actually run.
8. Every defect discovered during this increment's validation is recorded in the report with a classification (compliance-blocking or deferred improvement); every compliance-blocking defect is either resolved (with a reference to its corrective-maintenance commit/PR) and re-validated before this increment's closure, or explicitly left open with a stated reason and owner if closure is authorized by the operator with it still open.
9. The Final Prototype Validation Report is produced as a committed artifact in the repository (e.g., under `specs/` or `.marshal/reviews/`) and is internally traceable — every status claim in its matrices references the specific test, CI job, or manual-session evidence that produced it.

## Verification

- **Unit Testing:** re-execution of the existing `pytest` and `vitest` unit suites (AC 1); no new unit tests are authored by this increment beyond what a corrective-maintenance defect fix requires.
- **Integration Testing:** cross-component flows not previously exercised end-to-end — credential storage through the real Keychain adapter combined with a live/representative provider call and persistence (AC 4); interaction-independence check across two sequential interactions (AC 5); import-boundary and port-signature checks (AC 6).
- **Acceptance Testing:** the full packaged-application Clean Interaction → persistence → retrieval session (AC 2, AC 4); confirms system-level behavior matches established requirements from a user-equivalent entry point, complementing (not duplicating) the `desktop-package-smoke` CI job's narrower launch/readiness check.
- **Static Analysis:** `ruff check .`, `eslint` (AC 1); `core`/`adapters` boundary and port-signature diff checks (AC 6); traceability-matrix completeness review against `atria-t0.md` and each Increment 1–6 spec (AC 2, 3, 7).

## Constraints

- No new `core/`, `adapters/`, or `api/` capability, port, or data-model field is introduced by this increment itself; any code change arising from it is strictly a corrective-maintenance fix for a defect the validation identifies, scoped to the smallest change that resolves the defect, following the standard specification-amendment or defect-fix workflow for the affected increment's area.
- Previously approved Increment 1–6 acceptance criteria and specifications are not edited to accommodate a validation finding; a mismatch between implementation and an approved criterion is reported as a defect against the implementation.
- Increment 6's real Apple Developer Program signing/notarization PENDING item cannot be closed by this increment absent real credentials becoming available; it must be re-reported as PENDING, not silently dropped or marked passed.
- Reuse existing increments 1–6 verification evidence (test files, CI history, `.marshal/reviews`, `.marshal/pr-gate` records) wherever it already covers a requirement or acceptance criterion; this increment's new verification effort is concentrated on system-level, cross-increment, and packaged-artifact validation that could not have been exercised by any single prior increment's own gate.
- Marshal's role in this increment's cycle is the PR gate only (`marshal pr`); no standalone `marshal plan` or `marshal-cpd` invocation is required for this regular increment cycle, per the operator-authorized exemption in `CLAUDE.md` §0 / `.marshal/context/brief.md`. The PR gate's own internal review, cross-family debate, and security checks still run in full before any READY verdict.
- This increment is the terminus of the Implementation Plan's 7-increment sequence; its closure gates whether any future Optimize-phase work begins, per `atria-t0.md` §8 — that gating decision belongs to the operator, informed by the Final Prototype Validation Report, not to this specification or its implementation.
