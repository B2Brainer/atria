# Increment 3 — Persistence and Credentials

Status: Approved (2026-11-24) — amended during implementation (Keychain Data Protection deferral, same date)

Agentic workflow for this increment follows the established process: spec-creator (this document) → human approval → Claude Code implementation → test-engineer verification → code-reviewer independent review → Marshal complementary review per its configured discipline → human final approval and integration authorization (`commit` skill).

## Objective

Implement the persistence and credential adapters — `adapters/persistence/` (SQLite via SQLAlchemy, implementing `PersistencePort`) and `adapters/credentials/` (macOS Keychain, implementing `CredentialPort`) — so that `InteractionRecord`s are durably and verifiably persisted locally, and provider credentials are stored and retrieved securely, without any change to the established `core/` port contracts.

## Scope

**Included:**

- `adapters/persistence/`: a `PersistenceAdapter` implementing `PersistencePort` (`save(record) -> None`, `get(record_id) -> InteractionRecord`, `list_by_cycle(cycle_id) -> list[InteractionRecord]`) against a local SQLite database via SQLAlchemy.
  - Private operations (per Detailed Behavior): `serialize_record()` (invoked from `save()`) and `deserialize_record()` (invoked from `get()`/`list_by_cycle()`), translating between the Pydantic `InteractionRecord` (composing `InteractionRequest`, `InteractionResult`, `ExecutionMetrics`) and its SQLite-backed row representation.
  - A versioned schema/migration mechanism for the SQLite database (per the established Infrastructure decision, "Versioned SQLite migrations"), establishing the initial schema version for `InteractionRecord` and its composed models.
- `adapters/credentials/`: a `CredentialAdapter` implementing `CredentialPort` (`get(reference) -> str`, `store(reference, secret) -> None`, `delete(reference) -> None`) against the macOS Keychain.
  - Private operations (per Detailed Behavior): `read_keychain()`, `write_keychain()`, `remove_keychain()`.
- Unit and integration tests exercising both adapters against real infrastructure: a temporary/disposable SQLite file for the persistence adapter, and a test-scoped Keychain service/account namespace (or an equivalent verifiable macOS Keychain interaction) for the credential adapter — not against fakes, since the adapters themselves are what is under test in this increment.
- Round-trip verification: a saved `InteractionRecord` is retrievable with all fields, types, and the 0..1 composition cardinalities intact, across each independently relevant combination — `result` absent; `result` present with `metrics` present; and `result` present with `metrics` absent (the deserializer must not substitute a default/synthetic `ExecutionMetrics` for a genuinely absent one).

**Excluded:**

- `adapters/providers/` (real AI provider adapter via HTTPX) — Increment 4.
- `api/` and `desktop/` — Increments 5 and later.
- Packaging/distribution, code signing, notarization — Increment 6.
- Local backup and recovery procedures (an Infrastructure-level operational concern distinct from the persistence adapter's own correctness) — Increment 6, per the Implementation Plan's assignment of "Local backup and recovery" to that increment's deliverable.
- Resolution or persistence of `ProviderConfiguration` (`provider_id`, `endpoint`, `credential_reference`) as a stored/looked-up entity — see Open Decisions.
- Any modification to `core/ports/` signatures, or to `core/interaction/` / `core/records/` operations, unless a genuine defect is found and justified (none identified during this spec's preparation; the ports' signatures as implemented match the Interfaces specification exactly).
- Modifying `Brainer/teoria/` (authoritative doc, read-only).
- Restoring or referencing the pre-RESET implementation (historical material only; not a design reference).

## Expected Behavior

1. **`PersistenceAdapter.save(record)`** (public): serializes the given `InteractionRecord` — via `serialize_record()` (private) — into the SQLite schema and commits it, including its composed `InteractionRequest`, optional `InteractionResult`, and optional `ExecutionMetrics`. Calling `save()` with a record sharing an existing `record.id` updates that record (idempotent upsert) rather than producing a duplicate.
2. **`PersistenceAdapter.get(record_id)`** (public): retrieves the row(s) for the given `record_id` from SQLite and reconstructs an `InteractionRecord` via `deserialize_record()` (private), with all fields and composed sub-models restored to their original types and values. Requesting a non-existent `record_id` raises an exception (propagated, not translated, consistent with Increment 2's established propagation convention for port-boundary errors).
3. **`PersistenceAdapter.list_by_cycle(cycle_id)`** (public): retrieves all rows for the given `cycle_id`, deserializing each into an `InteractionRecord`; returns an empty list when no records exist for that cycle (not an exception), since this is a listing operation rather than a single-entity lookup.
4. **Schema versioning via a real migration mechanism.** The SQLite schema is established and evolved through a migration tool capable of applying ordered migrations from an arbitrary prior version to the current version (e.g., Alembic, already compatible with the established SQLAlchemy dependency) — not a hand-rolled "stamp a version number alongside `create_all()`" shortcut. A fresh, uninitialized database is brought to the current schema version by applying migration(s) in sequence; the mechanism records which migration(s) have been applied and is capable of applying any future migration added after this increment, in order, without data loss. This increment ships only the initial migration (the schema for `InteractionRecord` and its composed models), but the mechanism itself — not just today's schema — is what this increment delivers. **Migration ownership:** constructing a `PersistenceAdapter` against a given database path is itself responsible for ensuring that database is at the current schema version before returning — i.e., adapter construction runs any pending migration(s) automatically. No separate, out-of-band migration step is required (or permitted to be substituted) for ordinary use; `save()`/`get()`/`list_by_cycle()` must succeed on the very first call against a brand-new, empty database file, with no prior manual migration invocation by the caller or by a test.
5. **Durability across adapter recreation ("restart").** `PersistenceAdapter` and `CredentialAdapter` are constructed against a configured, stable location (a database file path; a Keychain service/account namespace) rather than any in-process or instance-scoped state. Data saved/stored by one adapter instance remains retrievable by a *newly constructed* adapter instance pointed at the same configured location, with no in-memory or per-instance cache required for correctness — simulating the adapter's behavior across an application restart.
6. **Credential identity and trust boundary.** `CredentialPort`'s `reference: str` maps deterministically to a concrete macOS Keychain identity (e.g., a fixed service name scoped to the application, with `reference` used as the Keychain account/key). Production and test runs use distinct, non-overlapping Keychain namespaces (e.g., a distinct service name or an environment-derived namespace prefix), so that test execution never reads, writes, or deletes a production credential entry, and vice versa. A locked, denied, or otherwise inaccessible Keychain surfaces as a propagated exception from `get()`/`store()`/`delete()` (consistent with the established propagation convention), not a silent no-op or a swallowed failure. This failure-propagation behavior must be demonstrated by a test that forces the underlying Keychain access library to report a denial/inaccessibility condition at the point `read_keychain()`/`write_keychain()`/`remove_keychain()` calls it (e.g., by injecting/mocking a failure response at that call site when a genuinely locked Keychain cannot be reliably produced in a test environment), asserting the adapter's public method raises rather than returning a falsy/empty/default value or swallowing the error.
7. **`CredentialAdapter.get(reference)`** (public): retrieves the secret associated with `reference` from the macOS Keychain via `read_keychain()` (private). Requesting a non-existent `reference` raises an exception (propagated).
8. **`CredentialAdapter.store(reference, secret)`** (public): writes `secret` under `reference` into the macOS Keychain via `write_keychain()` (private). Calling `store()` again with the same `reference` updates the stored secret (idempotent upsert), consistent with Keychain's native update-or-add semantics.
9. **`CredentialAdapter.delete(reference)`** (public): removes the Keychain entry for `reference` via `remove_keychain()` (private). After deletion, a subsequent `get(reference)` raises an exception, consistent with behavior 7.
10. **Independence from `core/`.** Both adapters depend only on `core/ports/` (the abstract contracts they implement) and the data models they serialize/deserialize; `core/` has no dependency on `adapters/`, SQLAlchemy, or any Keychain-specific library — unchanged from Increment 2's established boundary.
11. **No credential material in persisted records or logs.** `InteractionRecord`/`InteractionRequest` carry no raw secret; the persistence adapter never writes a credential value to SQLite, and neither adapter logs a secret value.
12. **Numeric fidelity through serialization.** `ExecutionMetrics.cost` (`Decimal`) round-trips through SQLite without precision loss or representation drift (e.g., stored as a fixed-point/string-backed column, not an approximate floating-point column).
13. **Keychain targeting (amended — operator-approved deviation, 2026-11-24).** `kSecUseDataProtectionKeychain` requires the calling process to be code-signed with a `keychain-access-groups` entitlement; verified directly during implementation that every `SecItem*` call fails with `errSecMissingEntitlement` under an unsigned interpreter, which is this prototype's only environment until Increment 6 (packaging/code signing/notarization) ships a signed binary. Requiring it in Increment 3 would make the real-Keychain integration tests (criterion 20 below) impossible to run non-skipped anywhere today, contradicting that same criterion. **Revised:** `CredentialAdapter` targets the legacy file-based macOS Keychain (the default `SecItem*` target when `kSecUseDataProtectionKeychain` is omitted) for this increment; `kSecUseDataProtectionKeychain` is deferred to Increment 6, to be added once a signed binary and its entitlement exist. The one and only accessibility class `CredentialAdapter` ever requests for an item it creates is `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` — not merely "a value no weaker than" it, but exactly that value, with no code path permitted to request any other class; this accessibility guarantee holds on the legacy keychain as well, independent of the Data Protection keychain question.

## Acceptance Criteria

1. `adapters/persistence/` defines a `PersistenceAdapter` class implementing `PersistencePort` (`save`, `get`, `list_by_cycle`) using SQLAlchemy against a local SQLite database.
2. Saving an `InteractionRecord` with a populated `result` (including `metrics`) and retrieving it via `get(record.id)` returns an equal `InteractionRecord` (all fields, including `cycle_id`, `sequence`, `request`, `result.output`, `result.status`, `result.metrics.input_tokens/output_tokens/duration/cost`, `created_at`).
3. Saving an `InteractionRecord` with `result=None` and retrieving it via `get(record.id)` returns a record with `result` still `None` (0..1 cardinality preserved through the round trip).
4. Saving an `InteractionRecord` with `result` present and `result.metrics=None` and retrieving it via `get(record.id)` returns a record with `result` present and `result.metrics` still `None` (not a default/synthetic `ExecutionMetrics` manufactured by the deserializer) — distinct from, and in addition to, criteria 2 (result + metrics both present) and 3 (result absent).
5. `list_by_cycle(cycle_id)` returns every `InteractionRecord` previously saved for that `cycle_id`, and none belonging to a different cycle; it returns an empty list for a `cycle_id` with no saved records.
6. `get(record_id)` raises an exception for a `record_id` that was never saved (or was not saved under that id).
7. Calling `save()` twice with records sharing the same `id` results in exactly one retrievable record under that `id`, reflecting the most recent save (idempotent upsert, not a duplicate).
8. The SQLite schema is established and advanced through a migration tool applying ordered migrations (e.g., Alembic): initializing a fresh, empty database file applies the initial migration and records it as applied; a test confirms both (a) the applied-migration record after initialization, and (b) that the mechanism can apply a second, test-only migration on top of the first in sequence (proving ordered-application capability, not just a static version stamp alongside `create_all()`).
9. Constructing a `PersistenceAdapter` against a brand-new, empty database file/path and immediately calling `save()` followed by `get()` succeeds with no prior out-of-band migration step performed by the test or caller — demonstrating that adapter construction itself is responsible for bringing the database to the current schema version.
10. A `PersistenceAdapter` instance saves a record, is discarded, and a *newly constructed* `PersistenceAdapter` instance pointed at the same database file path retrieves that record via `get()` with all fields intact (durability across adapter recreation / simulated application restart).
11. End-to-end future-migration discovery: a `PersistenceAdapter` is constructed against a fresh database file (bringing it to the then-current schema version, e.g. v1) and a record is saved via `save()`; a second, test-only migration (v2, additive) is then introduced; a *newly constructed* `PersistenceAdapter` instance, pointed at that same (still-v1) database file, is constructed with no manual/out-of-band migration step performed by the test — and this construction alone brings the database to v2 — after which the previously saved v1 record is still retrievable, unchanged, via `get()`.
12. `adapters/credentials/` defines a `CredentialAdapter` class implementing `CredentialPort` (`get`, `store`, `delete`) against the macOS Keychain, using a defined, documented `reference` → Keychain service/account mapping.
13. `store(reference, secret)` followed by `get(reference)` returns the same `secret` value.
14. A `CredentialAdapter` instance stores a secret, is discarded, and a *newly constructed* `CredentialAdapter` instance pointed at the same configured Keychain service namespace retrieves that secret via `get()` (durability across adapter recreation / simulated application restart).
15. `store(reference, secret_a)` followed by `store(reference, secret_b)` followed by `get(reference)` returns `secret_b` (update, not a duplicate/conflicting entry).
16. `delete(reference)` followed by `get(reference)` raises an exception.
17. `get(reference)` for a `reference` never stored (or already deleted) raises an exception.
18. With the underlying Keychain access library forced (via injected/mocked failure at the `read_keychain()`/`write_keychain()`/`remove_keychain()` call site) to report a locked/denied/inaccessible condition, each of `get()`, `store()`, and `delete()` raises (propagates) rather than returning a falsy/empty/default value or swallowing the failure.
19. Test-suite Keychain operations run under a namespace (service name and/or account prefix) distinct from any namespace a production build would use, verifiable by inspecting the configured service identifier used in tests versus the adapter's documented production default.
20. The real-Keychain integration tests (criteria 12–18) have run — not skipped — against an actual macOS Keychain at least once as part of this increment's verification evidence (locally on macOS and/or on a macOS CI runner); a non-macOS CI runner may skip them as a documented fallback, but that skip path must not be the only execution this increment ever demonstrates, and the evidence of the real run (e.g., a captured local/CI run log) is reported alongside this increment's verification results.
21. A saved `ExecutionMetrics.cost` value with at least two decimal places of precision (e.g., `Decimal("12.345")`) is retrieved via `get()` as an exactly equal `Decimal`, with no floating-point rounding drift.
22. No test or production code path writes a raw secret value to the SQLite database or to a log statement (confirmed by code review / targeted inspection of adapter code paths that touch both credentials and persistence).
23. A test monitors/intercepts process-creation calls (`subprocess.Popen`, `subprocess.run`, `os.exec*`, `os.posix_spawn`, or equivalent) for the duration of a `store()`, `get()`, and `delete()` call each, and asserts none is invoked — catching a subprocess spawned transitively by the chosen access library's dependencies, not just by `adapters/credentials/`'s own source. `store()` does not request a weaker-than-default Keychain item accessibility/protection class (confirmed by static/grep-based inspection, alongside criterion 22).
24. A test verifies, at the effective-configuration level (not adapter-source grep alone), that an item created by `store()` carries the exact accessibility class `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` and that no code path sets `kSecUseDataProtectionKeychain` (deferred to Increment 6, per criterion 13's amendment) — by spying on/inspecting the actual query dictionary passed to the PyObjC `SecItemAdd` call at the call site, or (if more practical to implement) by reading the stored item's attributes back via `SecItemCopyMatching` after `store()` and confirming the exact accessibility class — not merely confirming the attribute name appears somewhere in adapter source.
25. `core/` continues to have no import dependency on `adapters/`, `sqlalchemy`, or any Keychain-access library; `adapters/persistence/` and `adapters/credentials/` import only from `core/ports/`, the data models, and their respective infrastructure libraries (confirmed by static inspection).
26. `uv run pytest -q` passes with zero failures against the full test suite (Increments 1–3 combined), and `uv run ruff check .` reports zero errors.

- **Code Review** (criteria 22, 23, 24, 25, independent, per `code-reviewer`): confirms no secret material reaches SQLite, logs, or a subprocess argument list; confirms the no-subprocess-spawn and Data-Protection-keychain tests genuinely exercise the real call path (not a stub that bypasses the library); confirms the adapter/core dependency direction is preserved.
- **Acceptance Testing** (criteria 20, 26): captured evidence that the real-Keychain integration tests executed (not skipped) at least once, and a clean-checkout run of `uv run pytest -q` and `uv run ruff check .`, per `AGENTS.md`'s established verification commands.

## Constraints

- No new dependency beyond SQLAlchemy (already declared in `pyproject.toml` since Increment 1), a real migration tool compatible with SQLAlchemy (Alembic, unless implementation identifies a concrete reason to deviate, which must be justified at implementation time), and a macOS-native, in-process credential-storage binding: `pyobjc-framework-Security` (direct PyObjC bindings to the macOS Security framework's `SecItemAdd`/`SecItemCopyMatching`/`SecItemUpdate`/`SecItemDelete` calls, executed in-process with no subprocess/CLI invocation), unless implementation identifies a concrete reason to deviate, justified at implementation time (same pattern as the Alembic constraint above). `keyring` is explicitly rejected as the default choice: it is itself a cross-platform credential-store abstraction (contradicting the established "no cross-platform credential-store abstraction is in scope" constraint below), and its backend-selection logic is not pinned to a verified in-process implementation by default — a deviation to a specific, named, version-pinned `keyring` backend confirmed (by inspection of that exact release, not assumption) to perform the Keychain call in-process via `ctypes`/direct framework bindings — never via a subprocess — would need the same implementation-time justification as any other deviation. Whichever approach is used, it must be macOS-specific and consistent with the established Infrastructure decision — no cross-platform credential-store abstraction is in scope, since the prototype targets macOS only.
- **Secret handling at the process boundary.** No code invoked during `store()`/`get()`/`delete()` — including transitively, through any dependency the chosen access library pulls in — ever spawns a subprocess (`subprocess.Popen`/`subprocess.run`/`os.exec*`/`os.posix_spawn` or equivalent) or passes a secret value as a command-line argument (e.g., shelling out to `security` with the secret on the invocation line); such an argument is visible to other processes via `ps`/process listing and is prohibited outright. This cannot be confirmed by adapter-source grep alone, since a transitive dependency could shell out beneath an in-process-looking call site; it requires the end-to-end check specified in acceptance criterion 23. Every `SecItemAdd`/`SecItemCopyMatching`/`SecItemUpdate`/`SecItemDelete` query dictionary `CredentialAdapter` constructs requests exactly `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` as the item's accessibility class — the one and only value ever requested, not merely a floor no weaker option may fall below. `kSecUseDataProtectionKeychain` is deliberately NOT set in this increment (see criterion 13's amendment: it requires a code-signing entitlement this prototype does not have until Increment 6); the adapter targets the legacy file-based Keychain, which still honors the requested accessibility class.
- HTTPX remains reserved for Increment 4 and must not be imported by this increment's adapters.
- `core/ports/` signatures (`PersistencePort`, `CredentialPort`) must not change; this increment implements them, it does not redefine them.
- The public/private operation marking from Detailed Behavior (`＋ save/get/list_by_cycle/get/store/delete` vs. `－ serialize_record/deserialize_record/read_keychain/write_keychain/remove_keychain`) must be preserved; private operations are internal to the adapters, not alternative public entry points.
- The `reference` → Keychain service/account mapping and the test/production namespace separation scheme (Expected Behavior item 6) must be fixed and documented in the implementation (e.g., in the adapter's module docstring or a constant), not left to ad hoc per-test choices.
- Tests that exercise the macOS Keychain must use the disposable, test-scoped namespace (Expected Behavior item 6) and must clean up entries they create, to avoid polluting the developer's or CI runner's real Keychain state; a non-macOS CI runner may skip these tests as a documented fallback, but a skip is never the sole evidence of this increment's Keychain verification — at least one real, non-skipped execution against an actual macOS Keychain (local or macOS CI) must be captured and reported (acceptance criterion 20), so the suite's overall "zero failures" result (criterion 25) cannot be satisfied by skipping the real-Keychain coverage everywhere it runs automatically.
- Changes to this specification's acceptance criteria to accommodate an implementation shortfall are not permitted; deviations must be reported, not silently reconciled.

## Open Decisions (require human resolution before or during implementation)

1. **`ProviderConfiguration` persistence/resolution is not this increment's deliverable.** `ProviderConfiguration` (`provider_id`, `endpoint`, `credential_reference`) is modeled in the Data specification and referenced ("selects") by `InteractionRequest`, but neither `PersistencePort` nor `CredentialPort`'s established signatures (Interfaces specification, confirmed unchanged since Increment 2) include any method for storing or looking up a `ProviderConfiguration` by `provider_id` — `PersistencePort` only persists `InteractionRecord`; `CredentialPort` only stores/retrieves a secret by an already-known `reference` string. The Detailed Behavior diagram's adapter-side nodes for this increment (`save/serialize_record`, `get/list_by_cycle/deserialize_record`, `get/store/delete` + Keychain operations) likewise show no `ProviderConfiguration`-specific path. Recommendation: treat `ProviderConfiguration` resolution (mapping a `provider_id` to its `endpoint` and `credential_reference`) as Increment 4's concern — the AI Provider Adapter is the component that would need a resolved `endpoint` to call out via HTTPX, and `core/interaction/operations.py`'s `select_provider()` (Increment 2) is where a `credential_reference` lookup already occurs ahead of the `CredentialPort.get()` call. This increment's `CredentialAdapter` only needs to accept whatever `reference` string it is given; it does not need to know how that reference was resolved from a `provider_id`. **Decision requested:** confirm this reading (no `ProviderConfiguration` storage/lookup mechanism is implemented in Increment 3), or redirect it into this increment's scope if the operator intends `ProviderConfiguration` to be persisted data rather than static/injected configuration — in which case the acceptance criteria above would need to be extended before implementation.
2. **Atomicity of `InteractionRecordManagement._assign_sequence()` under concurrent persistence writes is not addressed by this increment's acceptance criteria, pending confirmation.** The current implementation (`core/records/operations.py`) computes the next `sequence` via `list_by_cycle()` then `max(...) + 1` — a read-then-write pattern that races if two `save()` calls for the same `cycle_id` are in flight concurrently. No diagram (Preliminary Behavior, Detailed Behavior) models concurrent `initiate()` calls against the same `AIUsageCycle`; Increment 4's own deliverable ("a reproducible interaction workflow... verify Clean Interaction execution") describes a single reproducible workflow, not a concurrent one, and the prototype is a single-user desktop application (per `atria-t0.md` §1 Objective) with no multi-process or multi-window interaction model established anywhere in the authoritative documentation. Recommendation: treat concurrent-write atomicity as legitimately out of scope for Increment 3 — the race is not reachable under the application's established usage model (sequential, single-user interaction) — while allowing (not requiring) the `adapters/persistence/` schema to include a `UNIQUE(cycle_id, sequence)` constraint as a low-cost defensive measure that would surface a conflict loudly (an exception) rather than silently corrupt data, should the assumption ever be violated. **Decision requested:** confirm this scope exclusion (no retry/transaction-level atomicity guarantee required in Increment 3's acceptance criteria), or direct that a specific mechanism (e.g., a `SELECT ... FOR UPDATE`-equivalent, a single-writer transaction boundary spanning `assign_sequence()` + `save()`, or an application-level lock) be added as an acceptance criterion before implementation.

Resolving Open Decisions 1 and 2 before implementation is recommended, since both affect whether this increment's acceptance criteria are complete as written. Human confirmation is requested before implementation locks in the default interpretation stated above.
