# Increment 4 — AI Provider Integration

Status: Approved (2026-11-24)

Agentic workflow for this increment follows the established process: spec-creator (this document) → human approval → Claude Code implementation → test-engineer verification → code-reviewer independent review → Marshal complementary review per its configured discipline → human final approval and integration authorization (`commit` skill).

## Objective

Implement `adapters/providers/` — an `AIProviderAdapter` implementing `AIProviderPort` via HTTPX — and close the remaining gap left open by Increment 2's placeholder `select_provider()` and Increment 3's deferred `ProviderConfiguration` resolution, so that a `Clean Interaction` can execute end to end against a real AI provider over HTTPS and produce a complete, accurately recorded `InteractionRecord`, without changing any established port signature.

## Scope

**Included:**

- `adapters/providers/`: an `AIProviderAdapter` implementing `AIProviderPort` (`execute(request: InteractionRequest) -> InteractionResult`) that invokes an external AI provider over HTTPS via HTTPX.
  - Private operations (per Detailed Behavior), invoked only through `execute()`: `prepare_provider_request()`, `send_request()`, `normalize_response()`.
  - `ProviderConfiguration` resolution: `AIProviderAdapter` is constructed with a static, injected mapping of `provider_id -> ProviderConfiguration` (no new port, no persisted/looked-up entity — settled resolution of Increment 3's Open Decision 1; see "ProviderConfiguration Resolution" below).
  - Credential resolution: `prepare_provider_request()` resolves the configured `ProviderConfiguration.credential_reference` via an injected `CredentialPort` dependency and uses the returned secret to authenticate the outbound HTTPX request (e.g., an `Authorization` header). This keeps `AIProviderPort.execute(request)`'s signature exactly as established (`InteractionRequest -> InteractionResult`, no credential parameter) while still satisfying the Detailed Behavior flow from `CredentialPort`/Keychain resolution into the AI Provider Adapter's request preparation.
  - `send_request()`: performs the outbound HTTPS call via HTTPX to `ProviderConfiguration.endpoint`, with TLS certificate validation enabled (HTTPX's default; never disabled).
  - `normalize_response()`: translates the provider's HTTP response into an `InteractionResult` (`output`, `status`, `metrics`), including `ExecutionMetrics` (`input_tokens`, `output_tokens`, `duration`, `cost`) when the provider response supplies the data needed to compute them.
- A closing correction to `core/interaction/operations.py`'s `_select_provider()` (Increment 2's placeholder, explicitly flagged there as "deferred to Increments 3/4"): resolves `request.provider_id` against the same `provider_id -> ProviderConfiguration` mapping to validate, ahead of invoking `AIProviderPort.execute()`, that a configuration and a retrievable credential exist for the requested provider — failing fast (propagated exception) if either is missing, rather than deferring that discovery to a failed HTTPS call.
- A single, generic HTTP request/response contract for the adapter (request body assembled from `InteractionRequest.input`, `model_id`, `parameters`; response parsed into `InteractionResult`), since the authoritative documentation specifies no concrete third-party provider API — this increment does not implement provider-specific SDKs or multiple divergent wire formats, only one configurable HTTP contract exercised against at least one real external AI provider endpoint for acceptance evidence (see Verification).
- Failure handling: network errors, non-2xx HTTP responses, and malformed/unparseable provider responses surface as a propagated exception from `execute()` (consistent with the established propagation convention used by Increments 2 and 3), not a silently degraded or partial `InteractionResult`.
- Unit and integration tests exercising the adapter's request preparation, response normalization, and HTTP interaction against a local HTTP stub implementing the adapter's generic contract, plus the acceptance-level real-provider run described in Verification.
- End-to-end verification: a full `InteractionManagement.initiate()` call, backed by the real `AIProviderAdapter`, the Increment 3 `CredentialAdapter`, and the Increment 3 `PersistenceAdapter`, producing a complete, persisted `InteractionRecord` for a genuine Clean Interaction — the "reproducible interaction workflow" that is this increment's stated deliverable.

**Excluded:**

- `api/` and `desktop/` (Electron/React UI, IPC) — Increments 5 and later; this increment's workflow is exercised through `core/` and `adapters/` directly, not through a live UI or process boundary.
- Packaging/distribution, code signing, notarization — Increment 6.
- Provider-specific SDKs, multi-provider routing/fallback logic, streaming responses, or any capability beyond a single synchronous request/response HTTPX call per `execute()` — none of these are described by the authoritative documentation's Data/Interfaces/Detailed Behavior specifications for this component.
- Persistence or a dedicated lookup port for `ProviderConfiguration` — resolved in this increment as a static, injected mapping (see "ProviderConfiguration Resolution" below), not as stored/queryable data; introducing such a port/store, if ever needed, is a later increment's concern.
- Any further change to `core/ports/` signatures (`AIProviderPort`, `CredentialPort`, `PersistencePort`) — unchanged from Increments 2 and 3.
- Modifying `Brainer/teoria/` (authoritative doc, read-only).
- Restoring or referencing the pre-RESET implementation (historical material only; not a design reference).

### ProviderConfiguration Resolution (closing Increment 3's Open Decision 1)

Increment 3 flagged, and recommended deferring to this increment, how `ProviderConfiguration` (`provider_id`, `endpoint`, `credential_reference`) is resolved from a `provider_id`, since neither `PersistencePort` nor `CredentialPort` exposes a lookup for it. This specification settles that question, confirmed by the operator (2026-11-24): `ProviderConfiguration` is **static, injected configuration** — a `Mapping[str, ProviderConfiguration]` supplied at construction time to both `InteractionManagement` (for the fail-fast validation in `_select_provider()`) and `AIProviderAdapter` (for `endpoint` and `credential_reference` resolution in `prepare_provider_request()`) — not a persisted or dynamically looked-up entity, and not a new port.

## Expected Behavior

1. **`AIProviderAdapter.execute(request)`** (public): given a prepared `InteractionRequest` (already passed through `InteractionManagement._prepare_clean_interaction()`), executes `prepare_provider_request()` → `send_request()` → `normalize_response()` and returns the resulting `InteractionResult`.
2. **`_prepare_provider_request(request)`** (private): resolves `ProviderConfiguration` for `request.provider_id` from the adapter's injected mapping; raises a propagated exception if no configuration is registered for that `provider_id`. Resolves the configured `credential_reference` via the adapter's injected `CredentialPort.get()`; raises a propagated exception (per Increment 3's established `CredentialPort` failure behavior) if the credential cannot be retrieved. Assembles the outbound HTTP request (method, URL from `ProviderConfiguration.endpoint`, headers including the resolved credential, and a JSON body derived from `request.input`, `request.model_id`, and `request.parameters`).
3. **`_send_request(prepared_request)`** (private): issues the prepared HTTP request via HTTPX with TLS certificate validation enabled and an explicit, finite timeout (no indefinite hang on a non-responding provider); measures wall-clock duration for `ExecutionMetrics.duration`. Raises a propagated exception for a network-level failure or a non-2xx HTTP status.
4. **`_normalize_response(response)`** (private): parses the provider's HTTP response body into an `InteractionResult` (`output`, `status`, and `metrics` when input/output token counts and cost are derivable from the response). Raises a propagated exception if the response body cannot be parsed into the expected shape.
5. **`InteractionManagement._select_provider(request)`** (modified from Increment 2's placeholder): resolves `ProviderConfiguration` for `request.provider_id` from the same injected mapping used by `AIProviderAdapter`, and calls `CredentialPort.get(configuration.credential_reference)` to confirm the credential is retrievable, before invoking `AIProviderPort.execute()`. Raises a propagated exception (consistent with Increments 2/3's propagation convention) if the `provider_id` is unconfigured or the credential cannot be retrieved — failing fast, ahead of the HTTPX call, rather than surfacing only as an adapter-level failure.
6. **End-to-end Clean Interaction.** `InteractionManagement.initiate(request)`, constructed with a real `AIProviderAdapter`, a real `CredentialAdapter` (Increment 3), and an `InteractionRecordManagement` backed by a real `PersistenceAdapter` (Increment 3), executes a complete Clean Interaction against a genuine external AI provider endpoint and returns an `InteractionRecord` with a populated `request`, a populated `result` (including `metrics` when the provider response supplies the needed data), and a correctly assigned `sequence`; the returned record is independently retrievable via `InteractionRecordManagement.get()`/`list_by_cycle()` with no field loss.
7. **No credential material in the request body, the persisted record, or logs.** The resolved secret appears only in the HTTP request's authentication mechanism (e.g., a header); it is never included in the JSON body, never returned as part of `InteractionResult`, never persisted, and never logged — consistent with Increment 3's established no-secret-leakage behavior, extended to this increment's new outbound call.
8. **Independence from `core/`.** `AIProviderAdapter` depends only on `core/ports/` (`AIProviderPort`, `CredentialPort`) and the data models it consumes/produces; `core/` has no dependency on `adapters/providers/` or HTTPX — unchanged from Increments 2 and 3's established boundary.

## Acceptance Criteria

1. `adapters/providers/` defines an `AIProviderAdapter` class implementing `AIProviderPort` (`execute`) using HTTPX, with `prepare_provider_request()`, `send_request()`, and `normalize_response()` as its private operation chain, invoked only through `execute()`.
2. `AIProviderAdapter` is constructed with an injected `provider_id -> ProviderConfiguration` mapping and an injected `CredentialPort`; calling `execute()` with a `request.provider_id` present in that mapping and a retrievable credential issues exactly one HTTPX request to the mapped `ProviderConfiguration.endpoint`.
3. Calling `execute()` with a `request.provider_id` absent from the injected mapping raises a propagated exception, with no HTTPX request issued.
4. Calling `execute()` with a `provider_id` present in the mapping but whose `credential_reference` the injected `CredentialPort` cannot resolve (raises) propagates that exception, with no HTTPX request issued.
5. Given a successful (2xx) provider HTTP response carrying output text and token/cost data, `execute()` returns an `InteractionResult` with `status` reflecting success, `output` matching the response's output text, and `metrics` populated with `input_tokens`, `output_tokens`, `duration` (a positive measured value), and `cost` matching the response's accounting data.
6. Given a successful (2xx) provider HTTP response that does not carry metrics data, `execute()` returns an `InteractionResult` with `metrics=None` (not a synthetic/default `ExecutionMetrics`), consistent with the 0..1 cardinality established in the Data specification.
7. Given a non-2xx HTTP response from the provider, `execute()` raises a propagated exception; no `InteractionResult` is returned.
8. Given a network-level failure (connection refused, DNS failure, or timeout) during `send_request()`, `execute()` raises a propagated exception.
9. Given a provider HTTP response whose body cannot be parsed into the expected result shape, `execute()` raises a propagated exception from `normalize_response()`.
10. `send_request()` performs the outbound call with TLS certificate validation enabled (no `verify=False` or equivalent anywhere in the adapter) and with an explicit, finite request timeout configured.
11. `InteractionManagement._select_provider()` resolves `ProviderConfiguration` for `request.provider_id` from the same injected mapping and confirms credential retrievability via `CredentialPort.get()` before `AIProviderPort.execute()` is invoked; a test demonstrates this ordering (e.g., a provider/credential resolution failure prevents the adapter's `execute()` from being called at all).
12. Calling `InteractionManagement.initiate(request)` with an unconfigured `request.provider_id` raises a propagated exception at `_select_provider()`, before any `AIProviderPort.execute()` invocation.
13. An end-to-end test constructs `InteractionManagement` with a real `AIProviderAdapter`, a real `CredentialAdapter`, and a real `PersistenceAdapter` (per Increment 3), calls `initiate()` for a genuine Clean Interaction against the real OpenAI API endpoint, and confirms: (a) the returned `InteractionRecord` has a populated `request` and `result`; (b) the same record is retrievable, unchanged, via `InteractionRecordManagement.get()`; (c) no credential value appears in the persisted record or in captured log output.
14. A test confirms the resolved credential value is present in the outbound HTTPX request's authentication mechanism (e.g., header) and absent from the request's JSON body.
15. `core/` continues to have no import dependency on `adapters/providers/` or `httpx`; `adapters/providers/` imports only from `core/ports/`, the data models, and `httpx` (confirmed by static inspection).
16. `uv run pytest -q` passes with zero failures against the full test suite (Increments 1–4 combined), and `uv run ruff check .` reports zero errors.

## Verification

- **Unit Testing** (criteria 1, 2, 3, 4, 6, 9, 10, 15): isolated tests of `prepare_provider_request()`, `normalize_response()`, and the `provider_id`/credential resolution logic in `_select_provider()`, exercised against fakes/stubs for `CredentialPort` and a controlled HTTPX transport (e.g., HTTPX's `MockTransport`) so request assembly and response parsing are verified without a live network call.
- **Integration Testing** (criteria 5, 7, 8, 11, 12, 14): tests exercising `AIProviderAdapter.execute()` end to end against a local HTTP stub server implementing this increment's single generic request/response contract (success with metrics, success without metrics, non-2xx, malformed body, and a simulated network failure), plus `InteractionManagement.initiate()` wired with real adapters to confirm the fail-fast ordering ahead of `execute()`. A local stub is used — rather than a live third-party provider — for these criteria because they must be deterministic, free of network flakiness and provider cost, and independently reproducible in CI without a live API key; this differs from Increment 3's real-Keychain precedent, where the real infrastructure (macOS Keychain) is local, free, and deterministic, and therefore usable directly.
- **Acceptance Testing** (criterion 13, and criterion 16): a full Clean Interaction executed against the real OpenAI API, using a real, operator-supplied OpenAI API key resolved through a real `CredentialAdapter` instance and a real `PersistenceAdapter` instance — captured and reported as this increment's verification evidence (comparable to Increment 3's "real Keychain, at least once" evidence requirement), since this is the one case that must demonstrate the full stack working against an actual provider, not a stub; this test is not required to run unattended in CI (it depends on a live, costed, rate-limited external service and a provisioned credential) but must be executed and its result captured at least once as part of this increment's reported verification. A clean-checkout run of `uv run pytest -q` and `uv run ruff check .`, per `AGENTS.md`'s established verification commands, for the remaining automated suite.
- **Static Analysis** (criterion 15): inspection confirming the adapter/core dependency direction and import boundaries.
- **Code Review** (criteria 7, 8, 9, 10, 14, independent, per `code-reviewer`): confirms failure paths genuinely propagate rather than swallow or degrade; confirms TLS validation is never disabled; confirms no credential value reaches the JSON body, the persisted record, or a log statement.

## Constraints

- No new dependency beyond HTTPX (already declared in `pyproject.toml` since Increment 1); a local HTTP stub mechanism used for integration tests (e.g., HTTPX's own `MockTransport`, or a minimal local ASGI/WSGI test server) is test-only and must not be shipped as or confused with a production dependency.
- `core/ports/` signatures (`AIProviderPort`, `CredentialPort`, `PersistencePort`) must not change; this increment implements and consumes them, it does not redefine them.
- The public/private operation marking from Detailed Behavior (`＋ execute` vs. `－ prepare_provider_request/send_request/normalize_response`) must be preserved; private operations are internal to the adapter, not alternative public entry points.
- The `provider_id -> ProviderConfiguration` mapping is static, injected configuration (e.g., supplied at composition time, not persisted or dynamically fetched); it must not be hardcoded inside `AIProviderAdapter` or `InteractionManagement` in a way that prevents test-time substitution.
- No secret value (API key, token) may appear in source control, in a committed test fixture, in a log statement, or in the JSON body of an outbound request; a real-provider credential used for the acceptance-level test is supplied via the environment/a local, untracked source and retrieved through `CredentialAdapter`, never embedded in test code.
- The real external AI provider used for the acceptance-level verification (criterion 13) is OpenAI, confirmed by the operator (2026-11-24); its API is reachable over HTTPS and matches this increment's single generic request/response contract. The authoritative documentation names no specific provider; this specification does not generalize this choice beyond the acceptance-level test evidence, and the adapter's request/response contract remains the single generic HTTPX shape described in Scope, not an OpenAI-specific SDK or wire format.
- Changes to this specification's acceptance criteria to accommodate an implementation shortfall are not permitted; deviations must be reported, not silently reconciled.

## Resolved Decisions

All three decisions previously open for this specification have been resolved by the operator (2026-11-24). None remain open.

1. **`ProviderConfiguration` resolution mechanism.** Resolved: a static, injected `provider_id -> ProviderConfiguration` mapping (`Mapping[str, ProviderConfiguration]`), supplied at construction time to both `InteractionManagement` and `AIProviderAdapter` — not a new port, not a persisted or dynamically looked-up entity. Decided by: operator, 2026-11-24. This closes Increment 3's Open Decision 1 as described in "ProviderConfiguration Resolution" above.
2. **Credential delivery path into the provider call.** Resolved: `AIProviderAdapter` is constructed with its own injected `CredentialPort` dependency and resolves the configured secret internally within `prepare_provider_request()`; `InteractionManagement._select_provider()` performs an independent fail-fast existence/retrievability check using the same `CredentialPort`, ahead of invoking `AIProviderPort.execute()`. `AIProviderPort.execute(request)`'s signature is unchanged (no credential parameter). Decided by: operator, 2026-11-24.
3. **Choice of real AI provider for the acceptance-level test (criterion 13).** Resolved: OpenAI. The acceptance-level test (criterion 13) is executed against the real OpenAI API, using an operator-supplied OpenAI API key resolved through a real `CredentialAdapter` instance. Decided by: operator, 2026-11-24.
4. **Wire-shape concretization (PR-gate review round, raised during the `marshal pr` review gate).** During the PR-gate review, a critic read "the adapter's request/response contract remains the single generic HTTPX shape described in Scope, not an OpenAI-specific SDK or wire format" (Constraints, above) as requiring a provider-neutral request/response envelope, and flagged the implementation's concretization to OpenAI's actual Chat Completions wire shape (`{"model", "messages"}` request; `{"choices", "usage"}` response) as a possible contradiction. Resolved: that reading was not the intent — the authoritative documentation specifies no concrete third-party provider API at all, and criterion 13 requires a real run against the named acceptance-test provider (OpenAI), which is only possible against OpenAI's actual wire shape. "Single generic HTTP contract, not an OpenAI-specific SDK" means this increment does not build a multi-provider SDK abstraction or support multiple divergent wire formats — not that the one contract it does implement must be provider-neutral. `ProviderConfiguration.endpoint` remains fully configurable; only the body/response shape (and the per-model cost derivation in `PRICING_PER_MILLION_TOKENS`, since OpenAI's response carries no cost field) is fixed to this one, OpenAI-shaped contract. Decided by: operator, 2026-11-24 ("I also approve the OpenAI wire-shape interpretation. No additional provider-neutral abstraction is required.").
