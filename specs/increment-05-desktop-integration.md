# Increment 5 — Desktop Integration

Status: Approved (2026-11-24)

Agentic workflow for this increment follows the established process: spec-creator (this document) → human approval → Claude Code implementation → test-engineer verification → code-reviewer independent review → Marshal complementary review per its configured discipline → human final approval and integration authorization (`commit` skill).

## Objective

Implement the communication interface between the Electron desktop process and the Python application core, and build the React graphical interface, so that a user can initiate a Clean Interaction, see its result, and browse prior interaction records through a functioning desktop application — without changing any established `core/` or `adapters/` contract beyond the one narrowly justified `PersistencePort.list_cycles()` addition (see Scope).

## Scope

**Included:**

- `api/`: the entry-point layer composing `core/` and `adapters/`, exposing the established business operations (`InteractionManagement.initiate()`, `InteractionRecordManagement.get()`, `InteractionRecordManagement.list_by_cycle()`), the new `list_cycles()` operation (below), and the narrowly scoped credential operations defined below, to the desktop process over the resolved subprocess/stdio JSON-RPC transport. Seven operations in total: `initiate(request, cycle_id)`, `get(record_id)`, `list_by_cycle(cycle_id)`, `list_cycles()`, `set_credential(provider_id, secret)`, `get_credential_status(provider_id)`, `remove_credential(provider_id)`.
- **Multi-cycle, persisted conversation history (resolved):** the sidebar's persistent, grouped, reopenable conversation list requires discovering which `cycle_id`s exist in storage — an operation no existing `core/ports/` method supports. This increment adds exactly one new `core/ports/` method, `PersistencePort.list_cycles()`, implemented by `PersistenceAdapter` via a `SELECT DISTINCT cycle_id ... GROUP BY cycle_id` query ordered by most recent activity, and a corresponding `InteractionRecordManagement.list_cycles()` public operation delegating to it. `AIUsageCycle` remains the lightweight, non-persisted value object it already is (`id`, `created_at`); no new persisted entity is introduced. `api/` constructs `InteractionManagement` per active `cycle_id` as needed (not one fixed instance bound to a single cycle for the process lifetime); `InteractionManagement`'s own constructor/signature is unchanged. `initiate` takes the target `cycle_id` as an explicit sibling IPC parameter (not a new field on `InteractionRequest`).
- **IPC transport (resolved):** subprocess communication between the Electron main process and the Python backend, over the child process's stdin/stdout, framed as line-delimited JSON-RPC (one JSON-RPC message per line). The transport is implemented entirely within `api/` (Python side) and the Electron main process (TypeScript side); it introduces no new `core/` abstraction, port, or dependency — it is an implementation-layer protocol, not an application-core concern. Protocol stdout carries JSON-RPC messages only; diagnostic/log output is routed to stderr or a separate log sink, never interleaved with protocol stdout.
- **Backend lifecycle (resolved):** the Electron main process owns the Python backend's full lifecycle — spawning the child process on application launch, verifying its readiness before routing requests to it, detecting its crash or unexpected exit, applying a bounded restart policy, and terminating it gracefully (with no orphaned child process) on application quit.
- `desktop/`: the Electron main process, preload script, and React renderer, built on the TypeScript/Vite/Vitest/ESLint tooling already scaffolded in Increment 1.
  - Main process: owns the Python backend subprocess's lifecycle (above) and exposes its JSON-RPC operations to the renderer only through a preload-defined, minimal bridge (no direct Node/Python access from renderer code).
  - Renderer (React), two routes, confirmed by visual inspection of `Brainer/teoria/presentation/Atria — UI Mockups.html` (operator, 2026-11-24):
    - **Chat Workspace** (route): a persistent left sidebar (conversation history grouped as "Today"/"Yesterday"/"Previous 7 Days", titled by each conversation's first message, a "+ New interaction" control, a "Settings" link) alongside a main panel (provider/model picker, scrollable exchange thread with inline metric chips and a "View details" link per exchange, and a message composer). Selecting "Interaction Details" does not navigate away from this route; it opens the slide-in panel described below over the same view.
    - **Settings** (a genuinely separate route, its own sub-navigation: "Providers" and "Preferences"). Providers: one row per established provider (Anthropic, OpenAI, Google) showing a masked key preview and a status badge ("Configured" / "Not configured" — see the credential-status item below for "Key invalid" scope) when configured, with "Replace"/"Remove" actions, or a "Paste API key" input and "Save key" action when not configured; a caption stating keys are stored in the macOS Keychain and never written to the interaction record. Preferences: a default provider/model picker and toggle switches for interaction-level preferences.
  - **Interaction Details** is not an independent route: it is a right-side slide-in panel overlaid on the Chat Workspace route (confirmed by visual inspection), showing an "Overview" section (Provider, Model, Status, Type, Started, ID), a "Metrics" section (Latency, Input, Output, Tokens/s), "Input" and "Output" text sections, a "Parameters" section (Temperature, Max tokens, Credential), and "Copy record"/"Export JSON"/"Delete" actions, dismissible via a close control without leaving Chat Workspace.
  - Following the mockup's established layout, interaction pattern, and color palette (Light Blue `#B8DBD9`, Charcoal Blue `#40434E`, Ghost White `#F4F4F9`, Cinnamon Wood `#A1674A`, Ruby Red `#A41623`).
- Wiring the renderer, through the IPC bridge and `api/`, to:
  - submit an `InteractionRequest` for a given `cycle_id` and receive back the resulting `InteractionRecord` (Chat Workspace → `initiate(request, cycle_id)`);
  - retrieve a specific `InteractionRecord` by id (Interaction Details panel → `get()`);
  - list the `InteractionRecord`s of a cycle (Chat Workspace thread → `list_by_cycle()`);
  - list existing cycles to populate the sidebar's grouped conversation history (Chat Workspace sidebar → `list_cycles()`).
- **Credential configuration and status (resolved, narrow scope):** three distinct IPC operations, exposed by `api/` and reachable from the Settings screen:
  - `set_credential(provider_id, secret)` — write-only end to end: calls the already-established `CredentialAdapter.store()` (via `CredentialPort`, Increment 3) with the submitted value and returns only a success/failure outcome — never the stored secret, never any previously stored secret.
  - `get_credential_status(provider_id)` — a narrow, non-secret read returning `{configured: bool, status: "configured" | "not_configured", masked_preview: str | None}`, supporting the Settings screen's status badge and masked key preview. It never returns the actual secret value. The implementation may call the already-established `CredentialPort.get()` internally to determine whether a credential exists (catching its failure as the `"not_configured"` signal, a successful retrieval as `"configured"`); this introduces no new `core/ports/` contract — see Resolved Decision 5 and Constraints. When present, `masked_preview` is derived, inside `api/`, from the secret value returned by `CredentialPort.get()` (e.g., masking all but the last few characters); it is never derived from a new port capability, and the full unmasked secret never reaches the renderer, an exception message, or a log statement. **"Key invalid" is out of scope for this increment:** it would require a persisted "last known validity" signal derived from an observed provider auth failure, which no established increment currently records; inventing that persisted state is not justified by this increment's objective. Settings therefore surfaces only "Configured"/"Not configured" functionally; the mockup's "Key invalid" badge style remains an unimplemented presentation detail, not a functional capability of this increment.
  - `remove_credential(provider_id)` — calls the already-established `CredentialAdapter.delete()` (via `CredentialPort`, Increment 3) and returns only a success/failure outcome, supporting the Settings screen's "Remove" action.
  No operation returning a stored secret value is ever exposed to the renderer. `provider_id` and `endpoint` remain statically configured (unchanged from Increment 4); only `credential_reference` values become settable/removable/inspectable (status only) through these mechanisms.
- Serialization of the established data models (`InteractionRequest`, `InteractionResult`, `ExecutionMetrics`, `InteractionRecord`) across the IPC boundary, preserving every field and its established cardinality (e.g. `InteractionResult.metrics` as 0..1, not defaulted to a synthetic value).
- Desktop-side error presentation: a propagated exception from `core/` (per Increments 2–4's established propagation convention) surfaces to the user as a visible, non-crashing error state in the renderer, not an unhandled rejection or a silent failure.
- Unit and integration tests for `api/`'s composition and serialization logic, and for the Electron/React layer's IPC bridge and screen behavior, run through the established TypeScript tooling (Vitest) and Python tooling (Pytest).
- Minimal `npm run dev`/`electron` launch sufficient to run and manually/acceptance-verify the application end to end on a development machine. This increment does not package, sign, or notarize the application (Increment 6).

**Excluded:**

- Packaging, code signing, notarization, auto-update, and GitHub Releases distribution — Increment 6, per `atria-t0.md` §6.
- Any change to the established `AIProviderPort`/`CredentialPort` contracts or their Increment 3/4 adapter implementations, and any change to the established `PersistencePort` methods (`save()`, `get()`, `list_by_cycle()`) — this increment composes and exposes them as established; its one addition is the narrowly justified `PersistencePort.list_cycles()` (see Scope), not a redefinition of any existing method.
- Any new `core/` business logic or data model fields beyond what is already established (Increments 2–4), other than the one narrowly justified `list_cycles()` read operation; the UI otherwise consumes the existing shapes and operations, it does not drive new ones.
- Multi-provider selection UI, streaming responses, or any AI-interaction capability beyond the single synchronous Clean Interaction already implemented by `InteractionManagement.initiate()` — none of these are established by the authoritative documentation for this increment.
- A persisted/queryable mechanism for `ProviderConfiguration`: `provider_id` and `endpoint` remain statically configured (Increment 4); only `credential_reference` values become settable/removable/status-readable, and only through the already-established `CredentialPort.store()`/`.delete()`/`CredentialAdapter` (Increment 3) via the narrow credential operations above — no new `core/ports/` contract is introduced to support credentials, and no new persisted `ProviderConfiguration` entity is introduced.
- A persisted "last known credential validity" concept: `get_credential_status` reports only `configured`/`not_configured`; detecting and persisting an "invalid" (auth-failed) state from an observed provider error is out of scope for this increment (see the credential-status item above).
- Any new persisted `AIUsageCycle` entity: `AIUsageCycle` remains the lightweight, non-persisted value object already established (`id`, `created_at`); grouping persisted `InteractionRecord`s by `cycle_id` (already an indexed, stored column) is sufficient to reconstruct conversation history, so no new row/table for cycles is introduced.
- Any cycle-management port or operation beyond `list_cycles()`: cycle creation remains an `api/`-level orchestration concern (generating a `uuid4()` per "+ New interaction"), not a new `core/` operation; `list_cycles()` itself is justified narrowly by the sidebar's need to enumerate existing cycles and is not a general-purpose query capability.
- Modifying `Brainer/teoria/` (authoritative doc, read-only).

## Expected Behavior

1. **`api/` composition.** `api/` constructs a single, process-scoped `InteractionRecordManagement` and a per-`cycle_id` `InteractionManagement` (constructed as needed — on each `initiate()` call for a given cycle, or lazily cached per cycle for the session — not one fixed instance bound to a single cycle for the process lifetime), wired to the real `AIProviderAdapter`, `CredentialAdapter`, and `PersistenceAdapter` (Increments 3–4) and the static `ProviderConfiguration` mapping, and exposes exactly seven operations over the JSON-RPC transport: `initiate(request, cycle_id)`, `get(record_id)`, `list_by_cycle(cycle_id)`, `list_cycles()`, `set_credential(provider_id, secret)`, `get_credential_status(provider_id)`, `remove_credential(provider_id)`. No additional operation is exposed. `InteractionManagement`'s own constructor/signature is unchanged from Increments 2–4; only how many instances `api/` creates, and when, changes — `core/interaction/operations.py` requires no modification.
2. **JSON-RPC protocol shape.** Each request carries a request identifier (`id`); each response carries the same `id` so the caller can correlate it to its originating request. Messages are framed one-per-line (line-delimited JSON) over the backend subprocess's stdin/stdout. A successful response carries a `result`; a failed response carries an `error` object instead of `result`, making success and failure distinguishable without ambiguity. Process stdout is reserved exclusively for these JSON-RPC messages; all diagnostic/log output (from `api/` or the backend process) is written to stderr or a separate log sink, never interleaved with stdout.
3. **Backend lifecycle.** The Electron main process spawns the Python backend subprocess on application launch and performs a readiness check/handshake before routing any renderer request to it. If the backend process exits or crashes, the main process detects this and applies a bounded restart policy (a defined, finite number of restart attempts, not unbounded retries). On application quit, the main process terminates the backend subprocess gracefully, leaving no orphaned Python process. If the backend dies while a request is in flight, that request's caller receives a distinguishable error outcome rather than hanging indefinitely or the request silently vanishing.
4. **Request submission (Chat Workspace).** The user enters input and submits it within the active conversation (`cycle_id`); the renderer sends a serialized `InteractionRequest` together with that `cycle_id` across the IPC bridge; `api/` invokes `InteractionManagement.initiate(request, cycle_id)` on the composition instance for that cycle; the resulting `InteractionRecord` is serialized back and the renderer appends it to the exchange thread, presenting `result.output` (and `result.metrics`, when present) to the user, matching the Chat Workspace mockup's result presentation.
5. **Record retrieval (Interaction Details).** Selecting a prior interaction sends its `record_id` across the IPC bridge; `api/` invokes `InteractionRecordManagement.get()`; the renderer presents the returned `InteractionRecord`'s `request`, `result`, and `metrics` fields, matching the Interaction Details mockup.
6. **Record listing (cycle browsing).** The renderer requests the records for the active `cycle_id`; `api/` invokes `InteractionRecordManagement.list_by_cycle()`; the renderer presents them in their returned (sequence) order within the Chat Workspace thread.
6a. **Conversation discovery (sidebar history).** On loading the Chat Workspace, and after a new cycle's first record is saved, the renderer requests `list_cycles()`; `api/` invokes `InteractionRecordManagement.list_cycles()`, which delegates to `PersistencePort.list_cycles()`; the renderer groups the returned cycles into "Today"/"Yesterday"/"Previous 7 Days" by each cycle's most-recent-activity timestamp and derives each entry's displayed title from a truncation of its first record's `request.input` (a presentation-layer derivation; no new title field exists on any model). Selecting a sidebar entry re-opens that `cycle_id`'s conversation via `list_by_cycle(cycle_id)`.
6b. **New conversation creation.** Activating "+ New interaction" causes `api/` (reached through the renderer) to generate a new `cycle_id` (`uuid4()`) and begin a fresh, empty conversation under it; no persistence write occurs until the first `initiate()` call for that cycle actually saves a record (no synthetic/placeholder `InteractionRecord` is created).
7. **Credential configuration (Settings).** The user enters a credential value in the Settings screen and submits it; the renderer sends the `provider_id` and the secret value across the IPC bridge; `api/`'s `set_credential` operation calls `CredentialAdapter.store()` with the submitted value and returns only a success/failure outcome. No operation, success response, or error response ever returns a stored secret value (current or previously stored) to the renderer.
7a. **Credential status (Settings).** On loading the Settings → Providers screen, the renderer requests `get_credential_status(provider_id)` for each established provider; `api/`'s implementation determines existence by calling the already-established `CredentialPort.get()` internally (its failure signals `"not_configured"`, a successful retrieval signals `"configured"`) — no new `core/ports/` method is introduced to support this. `api/` reports `{configured, status, masked_preview}` without ever including the retrieved secret value itself in the response, in any exception message surfaced to the renderer, or in any log statement; the renderer renders the "Configured" or "Not configured" badge and the masked preview accordingly (the mockup's "Key invalid" badge is not functionally produced by this increment — see Scope).
7b. **Credential removal (Settings).** Activating "Remove" on a configured provider row sends `remove_credential(provider_id)` across the IPC bridge; `api/` calls `CredentialAdapter.delete()` and returns only a success/failure outcome; on success the renderer updates that provider's row to its "not configured" state.
8. **Cycle identity and construction, not persistence of `AIUsageCycle` itself.** `AIUsageCycle` remains a lightweight, non-persisted value object (`id`, `created_at`), constructed on demand (e.g., when a new conversation is created, per item 6b); conversation existence and grouping are derived entirely from persisted `InteractionRecord.cycle_id` values via `list_cycles()`. No new cycle-management port beyond `list_cycles()` is introduced.
9. **Failure propagation.** A propagated exception from any of the seven exposed operations (e.g. unconfigured provider, unretrievable credential, provider/network failure, record not found, unknown cycle) is translated, at the IPC boundary, into a serializable error outcome (per item 2's success/error distinction); the renderer presents this as a visible error state to the user and does not crash, hang, or silently discard the failed action.
10. **No credential material crosses the IPC boundary or appears in the renderer.** Consistent with Increments 3–4's no-secret-leakage behavior, no resolved secret, credential reference value, or raw provider authentication header is ever included in a serialized `InteractionRequest`/`InteractionResult`/`InteractionRecord`/error outcome sent to the renderer, in any response to `set_credential`, `get_credential_status`, or `remove_credential`, logged by the main process, logged by the backend, or logged by the renderer. The only direction a secret value travels is renderer → main → `api/` → `CredentialAdapter.store()`.
11. **Renderer isolation.** The React renderer has no direct access to Node.js APIs or the Python process; it communicates exclusively through the preload-exposed bridge (Electron `contextIsolation: true`, `nodeIntegration: false` in the renderer), consistent with Electron's established security model.
12. **No unauthorized change to `core/`/`adapters/` contracts.** `core/ports/` signatures and the Increment 3/4 adapters are consumed as established, with exactly one addition: `PersistencePort.list_cycles()` (and its `PersistenceAdapter` implementation), justified narrowly by the sidebar's need to enumerate existing cycles (see Scope). This increment adds no other new port, no new adapter method, and no new field to `InteractionRequest`, `InteractionResult`, `ExecutionMetrics`, `InteractionRecord`, or `AIUsageCycle`.

## Acceptance Criteria

1. `api/` exposes exactly seven callable operations — `initiate(request, cycle_id)`, `get(record_id)`, `list_by_cycle(cycle_id)`, `list_cycles()`, `set_credential(provider_id, secret)`, `get_credential_status(provider_id)`, `remove_credential(provider_id)` — `initiate`, `get`, and `list_by_cycle` each delegating to the corresponding established `core/` operation without altering its input/output shape beyond the added `cycle_id` parameter on `initiate`.
2. A test confirms `api/`'s composition wires a real `AIProviderAdapter`, `CredentialAdapter`, and `PersistenceAdapter` (Increments 3–4), not fakes, when constructed for application use.
3. A test confirms JSON-RPC message framing and correlation: for a request sent with a given `id`, the corresponding response carries the same `id`; a successful response carries a `result` and no `error`; a failed response carries an `error` and no `result` — the two are distinguishable by a client inspecting the message alone.
4. A static check or test confirms that process stdout, across a representative run including log-producing code paths (e.g., an error condition, a startup message), carries only well-formed JSON-RPC messages — no log line, print statement, or diagnostic text is ever written to stdout; diagnostic output is confirmed to go to stderr or a separate log sink instead.
5. A test simulates the Python backend crashing (process exit) while a request is in flight, and confirms: the pending request's caller receives a distinguishable error outcome rather than hanging or losing the request silently; the main process detects the exit and relaunches the backend per the resolved bounded restart policy (a finite, defined number of attempts); and, separately, a test confirms that on application quit, no Python backend process remains running (no orphaned process).
6. Submitting a request through the renderer's Chat Workspace screen results in exactly one `initiate(request, cycle_id)` invocation reaching `InteractionManagement`, with the submitted `input`, `provider_id`, `model_id`, and `parameters` preserved unchanged in the `InteractionRequest` that reaches `core/`, and the active conversation's `cycle_id` passed unchanged.
7. On a successful `initiate()` call, the renderer displays the returned `InteractionRecord`'s `result.output`; when `result.metrics` is present, the renderer displays `input_tokens`, `output_tokens`, `duration`, and `cost`; when `result.metrics` is `None`, the renderer does not display synthetic/default metrics values.
8. Selecting a record in the renderer invokes `get(record_id)` with the selected record's id and displays the returned `InteractionRecord`'s `request` and `result` fields unchanged (no field loss across the IPC boundary), presented in the Interaction Details slide-in panel over the Chat Workspace view (not a navigation away from it).
9. Requesting the record list for a cycle invokes `list_by_cycle(cycle_id)` and the renderer displays the returned records in the order returned (established sequence order).
10. A test confirms `PersistencePort.list_cycles()`/`PersistenceAdapter.list_cycles()` returns every distinct `cycle_id` present in storage ordered by most recent activity; invoking `list_cycles()` through the renderer populates the sidebar's grouped conversation list, each entry titled from a truncation of its cycle's first record's `request.input`, with no new field added to any model to support this (confirmed by diff/static inspection).
11. Activating "+ New interaction" generates a new `cycle_id` and opens an empty conversation without any `PersistenceAdapter.save()` invocation occurring until the user's first submitted request for that cycle is saved (no synthetic/placeholder `InteractionRecord` is persisted).
12. A test inspects the serialized payload crossing the IPC boundary (both directions) for at least one credentialed Clean Interaction, and for `get_credential_status`/`remove_credential` calls, and confirms no credential value, credential reference's resolved secret, or raw provider authentication header appears anywhere in it.
13. Submitting a credential value through the Settings screen results in exactly one `CredentialAdapter.store()` invocation carrying the submitted provider identifier and secret value unchanged. No operation (including `set_credential`'s own success/error response, and every other exposed operation) ever returns a previously stored or currently submitted secret value to the renderer; the secret never appears in any IPC payload sent main → renderer, in any log statement (main process, backend, or renderer), or in any exception/error object surfaced to the renderer.
14. A test confirms `get_credential_status(provider_id)` returns only `{configured, status, masked_preview}` — never the stored secret — and that `status` takes only the values `"configured"` or `"not_configured"` (no "invalid" determination is produced by this increment, per Scope); a test confirms the implementation determines this status via an internal `CredentialPort.get()` call (success → `"configured"`, failure → `"not_configured"`) without the retrieved secret value appearing in the response, in an exception surfaced to the renderer, or in a log statement.
15. Activating "Remove" on a configured provider row results in exactly one `CredentialAdapter.delete()` invocation for that provider's `credential_reference`, and a subsequent `get_credential_status` call for that provider reports `configured: false`.
16. The Electron `BrowserWindow`'s renderer is configured with `contextIsolation: true` and `nodeIntegration: false`, confirmed by static inspection of the main process configuration.
17. The preload script exposes only the seven operations of criterion 1 (plus any strictly necessary request/response framing) to the renderer's global scope — no direct `require`, `fs`, `child_process`, or unrestricted Node API is reachable from renderer code (confirmed by static inspection).
18. The Chat Workspace and Settings screens are implemented as distinct React routes, each reachable through the application's navigation (Settings via the sidebar's "Settings" link and a "← Back to chat" return); Interaction Details is implemented as a slide-in panel overlaid on the Chat Workspace route (not a separate route), opened from an exchange's "View details" link and dismissed via its close control without leaving Chat Workspace.

## Constraints

- Exactly one new `core/ports/` contract addition is permitted in this increment — `PersistencePort.list_cycles()` — justified narrowly by the sidebar's conversation-discovery need; no other new port, and no new field on `InteractionRequest`, `InteractionResult`, `ExecutionMetrics`, `InteractionRecord`, or `AIUsageCycle`; this increment is otherwise additive only at the `api/`/`desktop/` layer.
- `AIUsageCycle` remains a non-persisted value object; conversation history is reconstructed entirely from `InteractionRecord.cycle_id`/`created_at` via `list_cycles()` and `list_by_cycle()` — no new table, row, or persisted entity for cycles is introduced.
- The subprocess/stdio JSON-RPC transport is implemented entirely within `api/` and the Electron main process; it introduces no new `core/` abstraction, port, or application-core dependency.
- Process stdout is reserved exclusively for JSON-RPC protocol messages; logging/diagnostic output must not interleave with it (stderr or a separate log sink only).
- The credential mechanisms (`set_credential`, `get_credential_status`, `remove_credential`) must each remain thin `api/`-layer wrappers around the already-established `CredentialPort`/`CredentialAdapter` (Increment 3) — not a new port — and no operation, response, log statement, or exception ever returns a stored secret value to the renderer. `get_credential_status` is restricted to `configured`/`status`/`masked_preview`; it must not be extended to resolve or return the secret itself. `get_credential_status`'s `api/`-layer implementation is permitted to call `CredentialPort.get()` internally (catching its failure as the "not configured" signal) and to derive `masked_preview` from the retrieved value, provided that value never appears in the response, an exception surfaced to the renderer, or a log statement; this internal retrieval does not constitute a second new `core/ports/` contract addition — the "exactly one new `core/ports/` contract addition" below (`PersistencePort.list_cycles()`) remains accurate.
- "Key invalid" credential-status detection is explicitly out of scope for this increment; no persisted "last known validity" state may be introduced to support it without a further specification decision.
- Electron's established security defaults apply: `contextIsolation: true`, `nodeIntegration: false` in the renderer, preload as the sole bridge surface (criteria 16–17).
- The renderer must follow the mockup's confirmed layout, screen set, interaction pattern, and color palette (Light Blue `#B8DBD9`, Charcoal Blue `#40434E`, Ghost White `#F4F4F9`, Cinnamon Wood `#A1674A`, Ruby Red `#A41623`), per the structural details captured in Scope and Design References; a deviation from the mockup's established pattern must be explained, per `CLAUDE.md` §5.
- No packaging, signing, notarization, or auto-update mechanism may be introduced in this increment; `electron-builder` remains reserved for Increment 6 and is not declared as a dependency here.
- Changes to this specification's acceptance criteria to accommodate an implementation shortfall are not permitted; deviations must be reported, not silently reconciled.

## Resolved Decisions

The operator resolved the following on 2026-11-24.

1. **IPC/communication transport between Electron and Python — resolved: subprocess + stdio/JSON-RPC.** Electron's main process spawns the Python backend as a child process and exchanges line-delimited JSON-RPC over stdin/stdout. No network port, no new HTTP dependency. The mechanism is confined to the implementation layer (`api/` and the Electron main process) and introduces no new `core/` abstraction. Request correlation (`id` matching), message framing (line-delimited), error propagation (distinguishable `error` vs. `result`), and separation of protocol stdout from diagnostic logs (stderr/log sink) are all required properties of the implementation, not left to the implementer's discretion. Resolved by: operator. Date: 2026-11-24.

2. **Python backend process lifecycle — resolved: Electron owns it.** The Electron main process owns the Python backend's full lifecycle: startup (spawn on launch), readiness verification before routing requests, failure detection (crash/unexpected exit), controlled/bounded restart, and graceful termination on quit. No orphaned backend process may survive application quit, and no in-flight request may be silently lost if the backend dies — it must surface as a distinguishable error. Resolved by: operator. Date: 2026-11-24.

3. **`ProviderConfiguration`/credential entry via Settings — resolved: narrow, write-only credential-configuration mechanism.** `provider_id` and `endpoint` remain statically configured, as established in Increment 4 (no new persistence, no new port for `ProviderConfiguration` itself). Users may configure API credentials through the existing `CredentialAdapter`, via a distinct IPC operation scoped specifically to credential configuration (not a business operation, and not merged into `initiate`/`get`/`list_by_cycle`). This operation is write-only: a secret value flows renderer → main → `api/` → `CredentialAdapter.store()`, and no operation ever returns a stored secret value back to the renderer; no secret appears in logs, exceptions, or interaction records. Resolved by: operator. Date: 2026-11-24.

4. **`AIUsageCycle` creation/selection — resolved (revised 2026-11-24): persisted, multi-cycle conversation history, grouped by `cycle_id`, discoverable via a new `list_cycles()` operation.** The operator overrode the prior "one in-memory cycle per application launch" resolution after visually inspecting the mockup's sidebar, which shows a persistent, grouped, reopenable conversation history — a capability a single in-memory per-launch cycle cannot support. `InteractionRecord` already carries `cycle_id`/`created_at`, and `PersistenceAdapter`'s SQLite table already stores `cycle_id` as an indexed column, so grouping persisted records into conversations by `cycle_id` is already supported by the existing data model: no new persisted `AIUsageCycle` entity is introduced, and `AIUsageCycle` remains the lightweight, non-persisted value object it already is. The one genuine gap is that `PersistencePort` exposes only `save()`, `get(record_id)`, and `list_by_cycle(cycle_id)` — every existing read requires already knowing a `cycle_id` or `record_id` — so there is no way to discover which cycles exist. This increment adds exactly one new method, `PersistencePort.list_cycles()` (and its `PersistenceAdapter` implementation via a `SELECT DISTINCT cycle_id ... GROUP BY cycle_id` query ordered by most recent activity), plus a corresponding `InteractionRecordManagement.list_cycles()` public operation delegating to it — the only new `core/ports/` surface this increment introduces, justified specifically by the inability to enumerate cycles without already knowing their ids, and not a general-purpose query capability beyond the sidebar's need. `api/`'s composition is revised accordingly: it constructs `InteractionManagement` per active `cycle_id` as needed rather than one fixed instance bound to a single cycle for the process lifetime; `InteractionManagement`'s own constructor/signature, and `core/interaction/operations.py`, are unchanged. `initiate` gains an explicit `cycle_id` sibling IPC parameter (not a new field on `InteractionRequest`, per the Constraints prohibition on new fields on established data models). Resolved by: operator. Date: 2026-11-24.

5. **Credential status read and removal — resolved: a narrow, non-secret `get_credential_status(provider_id)` read, plus `remove_credential(provider_id)` wrapping the already-established `CredentialPort.delete()`.** The Settings screen's status badges and masked key previews require a non-secret read of credential state; `get_credential_status(provider_id)` returns `{configured: bool, status: "configured" | "not_configured", masked_preview: str | None}` and never returns the actual secret. `CredentialPort` (`core/ports/credentials.py`) defines only `get(reference) -> str`, `store(reference, secret) -> None`, and `delete(reference) -> None` — there is no port-level "check existence/status" method, and none is introduced. `get_credential_status`'s `api/`-layer implementation is permitted to call the existing `CredentialPort.get()` internally to determine configured/not-configured status (catching its failure as the `"not_configured"` signal; a successful retrieval as `"configured"`), provided the retrieved secret value itself is never included in the response, in any exception message surfaced to the renderer, or in any log statement; when present, `masked_preview` is likewise derived, inside `api/`, from that retrieved value (e.g., masking all but the last few characters), never from a new port capability. This internal retrieval does not count as a second new `core/ports/` contract addition — the Constraints' "exactly one new `core/ports/` contract addition" (`PersistencePort.list_cycles()`) remains accurate. `CredentialPort`/`CredentialAdapter` (Increment 3) already define and implement `delete()`, confirmed by inspection of `core/ports/credentials.py` and `adapters/credentials/adapter.py`; `remove_credential(provider_id)` is a thin `api/`-layer wrapper around it, returning only a success/failure outcome, supporting the mockup's "Remove" action. The mockup's "Key invalid" badge state would require a persisted "last known validity" signal derived from an observed provider auth failure, which no established increment currently records; inventing that persisted state is not justified by this increment's objective, so it is explicitly out of scope here — Settings functionally supports only "Configured"/"Not configured" for this increment, with "Key invalid" remaining an unimplemented presentation detail in the mockup. Both operations are additive to, not a replacement for, the existing write-only `set_credential`; the secret itself remains write-only end to end across the IPC boundary (it is never returned to the renderer by any of the three operations), while internal, backend-side retrieval via `CredentialPort.get()` for status/masking purposes is a legitimate, trusted-process operation distinct from exposing the secret over IPC. Resolved by: operator. Date: 2026-11-24.

6. **Mockup fidelity — resolved: visually inspected by the operator.** The mockup (`Brainer/teoria/presentation/Atria — UI Mockups.html`) was rendered and visually inspected by the operator on 2026-11-24, via a local HTTP server, resolving the prior open item. Three screens were confirmed: Chat Workspace (persistent sidebar with "+ New interaction", grouped history "Today"/"Yesterday"/"Previous 7 Days", "Settings" link; main panel with provider/model picker, exchange thread with metric chips and "View details" links, and a composer); Interaction Details, confirmed to be a right-side slide-in panel overlaid on the Chat Workspace route — not a separate route — with Overview/Metrics/Input/Output/Parameters sections and Copy record/Export JSON/Delete actions; Settings, confirmed to be a genuinely separate route with its own "Providers"/"Preferences" sub-navigation, the Providers tab showing per-provider masked key previews, status badges, Replace/Remove actions (configured) or a Paste API key/Save key input (not configured), and a Keychain-storage caption. The palette and typography already documented in this specification (`#B8DBD9`/`#40434E`/`#F4F4F9`/`#A1674A`/`#A41623`) were confirmed accurate; no correction was needed there. This structural detail is now reflected throughout Scope, Expected Behavior, Acceptance Criteria (notably criterion 18, correcting the prior assumption that all three screens are distinct routes), and Constraints. Resolved by: operator. Date: 2026-11-24.
