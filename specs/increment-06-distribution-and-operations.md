# Increment 6 — Distribution and Operations

Status: Ready for Approval

Agentic workflow for this increment follows the established process: spec-creator (this document) → human approval → Claude Code implementation → test-engineer verification → code-reviewer independent review → Marshal complementary review per its configured discipline → human final approval and integration authorization (`commit` skill).

## Objective

Configure desktop packaging, code signing, notarization, GitHub Actions release workflows, GitHub Releases distribution, manual installer-based updates, local structured logging, and local data backup/recovery, so that the application built in Increments 1–5 can be built, distributed, and operated as an installable macOS prototype through a repeatable process — without changing any established `core/`, `adapters/`, or `api/` business behavior beyond the operational instrumentation this increment requires (structured logging calls, pre-migration backup).

## Scope

**Included:**

- **Desktop packaging:** `electron-builder` configuration under `desktop/` producing an installable macOS application artifact (`.dmg` and/or `.zip`) from the existing Electron main/preload/renderer build (Increment 5), bundling the Python backend (`api/`, `core/`, `adapters/`) so the packaged application runs without requiring the end user to separately install Python, `uv`, or Node.js development tooling. The bundling mechanism is a standalone Python runtime obtained through `uv` (e.g., `uv python install`'s managed CPython distribution together with a `uv export`/`uv sync --locked`-produced locked dependency set), bundled into the packaged application via `electron-builder`'s `extraResource` (or equivalent) mechanism — no additional packaging/freezing technology (e.g., PyInstaller) is introduced. Implementation must verify this mechanism's compatibility with: the locked `uv.lock`/`pyproject.toml` dependency set; the macOS Keychain integration in `adapters/credentials` (how it invokes/binds to Keychain, and whether that continues to work from a bundled, standalone Python runtime rather than a `uv`-managed dev environment); Alembic's ability to locate `adapters/persistence/migrations/versions/` from a bundled-resource path at runtime (not a dev-tree-relative path); and the backend subprocess lifecycle in `desktop/src/main/backend.ts` (the spawn/restart logic established in Increment 5 must spawn the bundled standalone-runtime executable/entry point in a packaged build, versus the `uv run` invocation used in development).
- **Code signing and notarization:** `electron-builder` configuration for macOS code signing (Developer ID Application certificate) and Apple notarization, implemented so that signing/notarization execute conditional on the required Apple Developer credentials being present as GitHub Actions secrets. Apple Developer Program enrollment is not assumed to be available now; the configuration and release workflow must be written to work correctly whenever those credentials are added later, without requiring them today. A build run without those secrets present (local or CI) still produces a runnable, unsigned development artifact for prototype validation, and that artifact is clearly and unambiguously distinguished from a signed+notarized distribution artifact (e.g., a filename suffix such as `-unsigned`/`-dev`, and/or a draft-vs-published GitHub Release distinction) — it is never mistakable for a release-quality artifact.
- **GitHub Actions release workflow:** a workflow (new or an addition to `.github/workflows/`) triggered by a version tag push, that builds the signed/notarized macOS artifact, and publishes it to GitHub Releases. Runs independently of the existing `ci.yml` (push/PR) workflow, which is unchanged in its own triggers and jobs.
- **Manual installer-based updates:** the established update mechanism is the user manually downloading and installing a new release artifact from GitHub Releases — no auto-update client, update-check network call, or background update mechanism is introduced (explicitly excluded, per the Implementation Plan's "manual installer-based updates").
- **Local structured logging and crash diagnostics:** replacing the current plain-text `logging.basicConfig` stderr-only configuration (`api/__main__.py`) with structured (JSON-lines) log records written to a local log file (in addition to or instead of stderr framing already established for the JSON-RPC transport in Increment 5 — stdout remains exclusively protocol messages, unchanged), at an OS-appropriate local application-data/log location, with size-based rotation: a maximum individual log file size of 5 MB, and a maximum of 3 retained rotated files (up to 4 files total on disk: the current active log file plus 3 rotated files); an uncaught exception in the Python backend or the Electron main process is captured as a log record (crash diagnostic) rather than being lost. No log record ever contains a credential, a resolved secret value, or sensitive interaction content (e.g., a raw prompt or response body, or a provider authentication header) — only non-sensitive operational metadata (operation name, identifiers, outcome, timing) is recorded (preserving and tightening Increment 5's established no-leakage behavior).
- **Versioned SQLite migrations:** the Alembic-based migration mechanism already established and exercised since Increment 3 (`adapters/persistence/migrations/`, run by `PersistenceAdapter._run_migrations()` on construction) is the established, continuing mechanism for schema evolution; this increment adds no new migration-running code path, but verifies the mechanism operates correctly inside the packaged application (the bundled Python environment can locate and apply `adapters/persistence/migrations/versions/` at runtime) and defines the one new migration-adjacent behavior below (pre-migration backup).
- **Local backup and recovery:** before `PersistenceAdapter` applies any pending migration whose target revision is not already the database's current revision, it produces a consistent, recoverable backup of the existing SQLite database before invoking `alembic upgrade`; no backup is taken when the database is already at the target revision (including first run, where no file yet exists). Because SQLite in WAL mode (or with a pending rollback journal) can leave a plain copy of only the main database file inconsistent, implementation must first determine `adapters/persistence/adapter.py`'s current SQLAlchemy/SQLite journal-mode configuration and handle it correctly — either checkpointing the WAL into the main database file before copying it, or capturing the `-wal`/`-shm` sidecar files alongside the main file, whichever the adapter's actual configuration makes the correct approach — so the resulting backup is independently restorable, not merely a byte-identical copy of the main file. This is a filesystem-level operational safeguard, not a new `core/ports/` capability or persisted entity. Restoration is a documented manual procedure (replacing the current database file — and sidecar files, if applicable — with a chosen backup while the application is not running) — no new restore operation, UI, or IPC call is introduced (see Scope exclusions).
- Tests for: the pre-migration backup behavior (`adapters/persistence/`); the structured log record shape and the stdout/log-sink separation (`api/`); presence and shape of the `electron-builder` and release-workflow configuration (static/config-level checks, per Verification).
- Documentation (e.g., `AGENTS.md` or a dedicated operational note) of: the release process (tag → CI build → signed/notarized artifact → GitHub Release), the manual backup-restore procedure, and the local log file location.

**Excluded:**

- Any new `core/` business operation, port, or data-model field: logging and backup are implementation-layer/operational instrumentation attached to existing operations (`PersistenceAdapter` construction, process entry points), not new application behavior exposed to `api/` or the renderer.
- An automated update-check, update-download, or update-install mechanism (auto-update): the Implementation Plan specifies "manual installer-based updates" — a user-driven download-and-reinstall from GitHub Releases is the complete mechanism for this increment.
- A restore operation reachable from the application UI or IPC surface: restoration is a manual, application-stopped filesystem procedure, documented but not automated, consistent with this increment's minimal operational scope for a local desktop prototype.
- Windows or Linux packaging, signing, or distribution: the established Infrastructure is macOS-only (`Compute: User's computer / macOS`).
- Telemetry, analytics, or any remote crash-reporting service: "crash diagnostics" is satisfied by local, structured log records; no telemetry/analytics service is named in the established Infrastructure and none is introduced.
- Any change to the established `InteractionRequest`/`InteractionResult`/`ExecutionMetrics`/`InteractionRecord`/`AIUsageCycle` models, the seven `api/` operations established in Increment 5, or the `core/ports/` contracts.
- Modifying `Brainer/teoria/` (authoritative doc, read-only) or any previously approved `specs/increment-0[1-5]-*.md`.
- Provisioning, purchasing, or being granted Apple Developer Program credentials: this specification requires the workflow and configuration to be *ready* to use real credentials when supplied, not that real credentials are available or exercised in this environment (see Acceptance Criteria 2–3 and Verification, PENDING items).

## Expected Behavior

1. **Packaged application launches and is self-contained.** Opening the packaged macOS application does not require Python, `uv`, Node.js, or any development tool to be separately installed on the target machine; the application spawns a working Python backend from within its own bundle and completes the established Increment 5 readiness handshake.
2. **Signed/notarized artifact, when credentials are present.** When the release workflow runs with the required signing/notarization secrets configured, the produced `.dmg`/`.zip` artifact is signed with a Developer ID Application certificate and successfully notarized by Apple before being attached to a GitHub Release; macOS Gatekeeper does not block the signed artifact's installation and first launch.
3. **Unsigned fallback build does not fail the pipeline.** When signing/notarization secrets are absent (e.g., a local or non-release CI build), packaging still produces a runnable artifact for development/manual verification, clearly distinguishable from a release artifact, without the build step failing outright for lack of secrets.
4. **Tag-triggered release.** Pushing a version tag (e.g., `v*`) triggers the release workflow, which builds the packaged artifact and publishes it to GitHub Releases, attached to that tag's release entry; the existing push/PR `ci.yml` workflow is unaffected (continues running its own jobs on its own triggers).
5. **No auto-update network call.** The packaged application makes no outbound request to check for, download, or install an update; obtaining a new version is entirely the user downloading and installing a new GitHub Release artifact.
6. **Structured logging.** Both the Python backend and the Electron main process emit log records in a structured (JSON-lines), parseable form to a local log file at an OS-appropriate location, distinct from process stdout (which remains reserved exclusively for JSON-RPC protocol messages, per Increment 5). The log file rotates by size: once the active log file reaches 5 MB it is rotated, and at most 3 rotated files are retained (4 files total on disk, including the active file) — older rotated files beyond that count are deleted. An uncaught exception in either process is captured as a log record before the process exits (where technically interceptable — e.g., a top-level exception handler/`uncaughtException` listener) rather than silently lost. No log record, in either process, ever contains a resolved secret, a credential reference's secret value, a raw provider authentication header, or sensitive interaction content (e.g., a raw prompt or response body) — only non-sensitive operational metadata (operation name, identifiers, outcome, timing) is recorded.
7. **Pre-migration backup.** On `PersistenceAdapter` construction, if the database file already exists and its current Alembic revision differs from the target (migration is about to run), the pre-migration database state is captured to a timestamped backup location before `alembic upgrade` executes, using whichever approach (WAL checkpoint-then-copy, or copying the main file together with its `-wal`/`-shm` sidecars) is correct for the adapter's actual SQLite journal-mode configuration; first run (no existing file) and an already-up-to-date database take no backup. The backup is sufficient to be manually restored — by replacing the live database file (and sidecar files, if applicable) with it while the application is not running — and, once restored, is openable by SQLAlchemy/Alembic with all pre-migration data readable and consistent (not merely byte-identical to the original file).
8. **Migration mechanism verified inside the packaged artifact.** The packaged application's bundled Python environment locates and applies `adapters/persistence/migrations/versions/` correctly at first run and on subsequent runs with a newer migration present, consistent with the mechanism already established and tested in Increment 3.
9. **No change to established business behavior.** `core/` operations, `core/ports/` contracts, the seven `api/` operations, and the renderer's established screens and IPC wiring (Increment 5) are unaffected; this increment's additions are confined to packaging configuration, the release workflow, logging implementation, and the pre-migration backup hook.

## Acceptance Criteria

1. A packaged macOS build artifact is produced from `desktop/` via `electron-builder`, launches, and successfully completes the backend readiness handshake without any development tool pre-installed on the target machine (verified on a clean macOS environment or VM).
2. A static/config check confirms `electron-builder` is configured for macOS code signing and notarization (the relevant configuration keys/environment variable references are present), and the release workflow supplies signing/notarization credentials from GitHub Actions secrets rather than from a hardcoded or committed value. **(Fully verifiable in this environment via static/config inspection.)** A further sub-check — that signing and notarization actually execute successfully and produce a Gatekeeper-passing artifact when real Apple Developer credentials are present as secrets — is **PENDING**: it requires real Apple Developer Program credentials not available in this environment, and cannot be marked passed without them.
3. A build run without signing/notarization secrets present (e.g., a developer's local build, or a non-tag CI run) completes successfully and produces a runnable, clearly non-release-labeled artifact rather than failing.
4. A test/static check confirms the release workflow triggers only on a version-tag push and is independent of (does not replace or alter the triggers/jobs of) the existing `ci.yml` workflow.
5. A static check confirms no auto-update dependency (e.g., `electron-updater`) is declared in `desktop/package.json`, and no outbound "check for update" network call exists in the packaged application's code.
6. A test confirms the Python backend's log output is structured (JSON-parseable) and written to a file, distinct from stdout; a test confirms stdout, across a representative run including log-producing code paths, still carries only well-formed JSON-RPC messages (re-confirming Increment 5's AC 4 continues to hold with structured logging in place); a test confirms the log file rotates once the active file reaches 5 MB, and that no more than 3 rotated files plus the active file (4 total) are retained on disk after repeated rotation.
7. A test confirms an uncaught exception in the Python backend produces a captured log record (not a silent process exit with no diagnostic trace).
8. A test confirms no log record produced by a representative run containing a credential operation (`set_credential`, `get_credential_status`, `remove_credential`) contains the secret value, a resolved provider authentication header, the full unmasked credential, or sensitive interaction content (e.g., a raw prompt/response body) — only non-sensitive identifiers and metadata (e.g., `provider_id`, operation name, outcome, timing) appear; a positive assertion confirms the relevant log-producing code path actually executed and produced a record (not merely the absence of a match).
9. A test confirms: constructing `PersistenceAdapter` against a pre-existing database file whose stored Alembic revision is behind the current migrations' head produces exactly one timestamped backup capturing the pre-migration database state, taken using the journal-mode-correct approach (WAL checkpoint-then-copy, or main file plus `-wal`/`-shm` sidecars, per the adapter's actual SQLite configuration); constructing it against a database already at head, or against no existing file, produces no backup. A second test actually restores the backup — copies it back to a database file location and opens it via SQLAlchemy/Alembic — and confirms the pre-migration data is present and readable, and the resulting database reports the pre-migration Alembic revision as current; a byte-identical-copy assertion alone does not satisfy this criterion.
10. A test confirms the packaged application's bundled Python environment successfully applies the established migration chain (`adapters/persistence/migrations/versions/`) on first run against a fresh database file, consistent with Increment 3's established mechanism.
11. A test or code-level diff confirms no `core/` module, `core/ports/` signature, `api/` operation surface, or established data model gains a new field or changed signature as a result of this increment (logging calls and the backup hook are additive, non-signature-changing instrumentation within `adapters/persistence/` and the process entry points only).

## Verification

- **Unit Testing:** pre-migration backup logic (journal-mode-correct capture, conditional triggering on revision mismatch, no backup on first run/already-current); structured log record shape, size-based rotation/retention, and redaction of credential operations and sensitive interaction content (AC 6–9).
- **Integration Testing:** migration application inside a constructed `PersistenceAdapter` against a fresh/behind-head database file (AC 9–10); backup restoration (copy-back, open via SQLAlchemy/Alembic, confirm readable/consistent pre-migration data and reported revision) (AC 9); stdout/log-sink separation under a representative run including error paths (AC 6).
- **Acceptance Testing:** manual verification of a packaged artifact's launch and backend readiness on a clean macOS environment (AC 1); manual verification of a signed/notarized release artifact's installability under Gatekeeper — **PENDING**, performed with real Apple Developer credentials once provisioned (AC 2) — this step cannot be exercised by this agent/session or in this environment and is explicitly deferred to a human or CI run with the real credentials configured; it must not be reported as passed absent that real-credential run.
- **Static Analysis:** `electron-builder` and release-workflow configuration presence and shape, including the conditional (secrets-present) signing/notarization path and the unsigned-fallback labeling (AC 2, 3, 4, 5); absence of an auto-update dependency (AC 5); diff/static confirmation of no unauthorized `core/`/`api/` signature changes (AC 11).

## Constraints

- No new `core/ports/` method, adapter method, or data-model field beyond the pre-migration backup hook (an internal `PersistenceAdapter` construction-time behavior, not a new port operation) and structured logging calls (instrumentation, not business logic).
- Logging implementations must preserve and tighten the already-established no-secret-leakage invariant (Increments 3–5): no secret, resolved credential, raw provider authentication header, or sensitive interaction content (e.g., a raw prompt/response body) may appear in a log record — only non-sensitive operational metadata (operation name, identifiers, outcome, timing). The log file is size-rotated at 5 MB with at most 3 rotated files retained (4 files total).
- Backup implementations must capture a consistent, independently-restorable database state given `adapters/persistence/adapter.py`'s actual SQLite journal-mode configuration (WAL checkpoint-then-copy, or main file plus `-wal`/`-shm` sidecars, as applicable) — a plain copy of only the main database file is not sufficient if it can be inconsistent under the adapter's configuration. The backup remains a copy of already-persisted, non-secret `InteractionRecord` data, consistent with Increment 3's established absence of credential storage in the interaction-record database.
- No additional Python packaging/freezing technology (e.g., PyInstaller) is introduced; the Python backend is bundled as a standalone `uv`-provisioned runtime with a locked dependency set via `electron-builder`'s `extraResource` (or equivalent) mechanism, per the resolved packaging approach.
- Signing/notarization credentials (Apple Developer ID certificate, app-specific password or API key) are supplied exclusively via GitHub Actions secrets, never committed to the repository or hardcoded in `electron-builder` configuration; their absence must not fail the build, only skip the signing/notarization step and clearly label the resulting artifact as unsigned/development.
- The release workflow must not weaken or bypass the existing `ci.yml` push/PR verification gate; a tag-triggered release build still depends on the codebase having passed the standard CI checks (via the established branch/PR workflow) before a tag is created.
- Windows/Linux targets, auto-update, telemetry, and an automated restore path are out of scope per the Implementation Plan's macOS-only, manually-updated, locally-logged prototype scope; none may be introduced under this specification.
- Any acceptance criterion or verification step that can only be exercised with real Apple Developer credentials (an actual signed/notarized artifact, a real Gatekeeper install test, a real notarization round-trip) must be reported as PENDING, not passed, until exercised with those real credentials.

## Open Decisions

The three open decisions carried in the prior draft (Python backend bundling mechanism, signing/notarization credential availability, log file retention/rotation policy) have been resolved by the operator, as reflected throughout this specification:

1. **Python backend bundling mechanism — resolved.** A standalone Python runtime provisioned via `uv` (e.g., `uv python install`), bundled with a `uv export`/`uv sync --locked`-produced locked dependency set, embedded via `electron-builder`'s `extraResource` (or equivalent) mechanism. No additional packaging/freezing tool (e.g., PyInstaller) is introduced. No concrete technical evidence surfaced during this revision indicating the standalone-runtime approach cannot work; implementation must still verify the compatibility points called out in Scope and Expected Behavior (Keychain integration, migration path resolution, subprocess spawn/restart) and report back if a concrete incompatibility is found during implementation — at which point it becomes a new open question, not a silent tool substitution.
2. **Signing/notarization credential availability — resolved.** Real Apple Developer Program credentials are not assumed to exist in this environment. The configuration and workflow are specified to work correctly whenever credentials are supplied as GitHub Actions secrets, without requiring them now; an unsigned, clearly-labeled development artifact is produced in their absence (AC 3). Verification of the signed/notarized path itself remains genuinely infeasible without real credentials and is marked PENDING (AC 2 sub-check; Verification, Acceptance Testing) rather than assumed passed.
3. **Log file retention/rotation policy — resolved.** Size-based rotation at a maximum of 5 MB per file, with at most 3 rotated files retained (4 files total on disk including the active file) — now a concrete, acceptance-testable parameter (Expected Behavior 6; AC 6).

No open decisions remain blocking approval.
